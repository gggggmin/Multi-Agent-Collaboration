> 写作日期：2026-09-21

## 摘要

随着 Web 应用业务流程复杂度持续提升，传统自动化测试脚本编写方式在需求理解、用例覆盖和脚本维护方面面临明显瓶颈。测试人员需要从自然语言需求文档中提炼测试点，再手工编写用例和自动化脚本；当需求变更或页面结构调整时，测试脚本又容易因定位器失效、断言不匹配等问题产生维护成本。大语言模型为需求理解和测试生成提供了新的技术路径，但单一模型直接生成测试用例时容易出现需求幻觉、边界遗漏和代码不可执行等问题。

针对上述问题，本文设计并实现了一种基于多智能体协同的需求驱动自动化测试生成与自愈框架。该框架首先通过检索增强生成技术对需求文档进行语义切片与知识检索，保留功能模块、操作路径和预期结果之间的业务语义；随后构建 Creator-Auditor 多智能体协同机制，由用例生成智能体负责生成正向、逆向和边界测试场景，由审计智能体对需求一致性和场景完备性进行校验；在代码生成阶段，框架将结构化测试用例映射为基于 Pytest、Playwright 和 Page Object Model 的自动化测试脚本；最后，框架引入执行反馈驱动的自愈模块，根据测试运行错误进行诊断和策略化修复，形成“需求理解-用例生成-脚本生成-执行反馈-自动修复”的闭环流程。为进一步增强算法性，本文将多智能体博弈终止建模为马尔可夫决策过程，采用 PPO 构建 RL-AGS 自适应终止策略，并将自愈策略选择建模为多臂赌博机问题，提出 RL-HSS 策略选择机制。

实验部分以本地 Flask 电商系统为被测对象，覆盖登录、商品搜索、购物车和结算四类典型业务模块。端到端验证结果表明，框架可生成 80 条测试用例及对应自动化脚本，需求覆盖率达到 100.0%，幻觉率为 0.0%，生成测试套件在本地环境下全部通过，Pytest 执行结果为 80 passed，耗时 394.67 秒。针对 Playwright strict mode 定位器冲突构造的自愈实验显示，系统能够将定位器类故障诊断为 locator 错误，并通过规则化修复策略完成脚本修复，修复前执行失败，修复后执行成功。针对模糊需求、冲突需求、幻觉用例和不完整用例构造的鲁棒性实验显示，审计智能体能够识别 12 个质量问题；同时，本文发现原始 PPO 策略在高风险状态下可能错误接受结果，因此进一步提出 Safety-gated RL-AGS 机制，在存在 error 级审计问题时强制继续迭代。此外，本文设计 RCP-TCP 测试用例优先级排序算法，对生成的 80 条测试用例进行执行前排序，使边界值和高风险用例优先进入执行队列。实验结果验证了所提方法在需求对齐、自动化代码生成、鲁棒性审计、执行排序和脚本自愈方面的可行性。

关键词：多智能体系统；自动化测试；测试用例生成；检索增强生成；大语言模型；脚本自愈

## Abstract

With the increasing complexity of Web application workflows, traditional automated test development suffers from low efficiency in requirement understanding, insufficient test coverage, and high script maintenance cost. Although large language models provide new opportunities for requirement-based test generation, directly using a single model may introduce hallucinated test cases, missed boundary scenarios, and non-executable scripts.

To address these problems, this thesis proposes and implements a requirement-driven automated test generation and self-healing framework based on multi-agent collaboration. The framework first uses retrieval-augmented generation to parse and retrieve requirement chunks. It then introduces a Creator-Auditor collaboration mechanism, where the Creator generates structured positive, negative, and boundary test cases, and the Auditor checks requirement consistency and completeness. The approved test cases are transformed into Pytest and Playwright scripts following the Page Object Model. To improve the algorithmic decision process, this thesis models the stopping decision of the Creator-Auditor game as a Markov decision process and adopts PPO to build the RL-AGS adaptive stopping strategy. It also models healing strategy selection as a multi-armed bandit problem and proposes RL-HSS for adaptive script repair strategy selection.

Experiments are conducted on a local Flask-based e-commerce application covering login, product search, shopping cart, and checkout modules. The framework generates 80 test cases and executable test scripts, achieving 100.0% requirement coverage and 0.0% hallucination rate on the annotated requirement set. The generated suite passes all tests with 80 passed in 394.67 seconds. A locator-conflict self-healing experiment shows that the framework can diagnose and repair Playwright strict-mode locator failures. A robustness experiment with ambiguous requirements, conflicting requirements, hallucinated cases, and incomplete cases further demonstrates the effectiveness of the Auditor and motivates the proposed Safety-gated RL-AGS mechanism. In addition, the RCP-TCP prioritization algorithm ranks the generated test cases before execution so that boundary and high-risk cases are executed earlier.

Keywords: multi-agent system; automated testing; test case generation; retrieval-augmented generation; reinforcement learning; self-healing test automation

## 第1章 绪论

### 1.1 研究背景与意义

软件测试是保障软件质量的重要环节。对于 Web 应用、电子商务系统和企业管理系统而言，业务流程往往包含登录鉴权、检索筛选、购物车管理、订单结算、异常输入处理等多个互相关联的场景。传统自动化测试开发通常依赖测试人员阅读需求文档，人工拆解测试点，再编写测试用例和自动化脚本。这一流程虽然具有较强可控性，但在需求频繁变更、迭代节奏加快和系统界面持续演化的情况下，存在三个突出问题。

第一，需求到测试用例的转换依赖人工经验，容易出现覆盖不充分。测试人员需要在有限时间内识别正向流程、异常流程和边界条件，不同人员对需求的理解差异会直接影响测试质量。第二，自动化脚本编写成本较高。即使采用 Pytest、Playwright、Selenium 等成熟工具，测试人员仍需维护页面对象、操作流程、测试数据和断言逻辑。第三，脚本维护压力大。页面元素定位器、页面跳转流程或业务提示语发生变化时，原有脚本可能出现定位失败、超时或断言失败，进而影响持续集成流程的稳定性。

近年来，大语言模型在自然语言理解、代码生成和软件工程辅助任务中表现出较强能力，为自动化测试提供了新的技术基础。通过大语言模型，可以从自然语言需求中生成测试用例，也可以将测试步骤转换为代码。然而，直接使用单一大语言模型生成测试产物仍然存在明显风险：模型可能生成需求中不存在的功能，可能遗漏异常路径，也可能生成语法正确但无法执行的脚本。换句话说，大模型不是银弹，直接把需求扔进去等它吐出高质量测试代码，这思路听着省事，实际很容易翻车。

因此，本文将研究重点放在“受约束的智能生成”上，即通过 RAG 提供需求上下文，通过多智能体协同降低幻觉，通过执行反馈验证代码可运行性，并通过自愈机制处理常见脚本故障。该研究具有两个方面的意义：在工程层面，可减少需求分析和测试脚本维护成本；在学术层面，可探索多智能体协同机制在测试生成任务中的作用，为大语言模型驱动的软件测试研究提供可复现原型。

### 1.2 国内外研究现状

现有研究主要集中在四个方向。

第一，基于大语言模型的测试用例生成。相关研究表明，大语言模型具备从需求、代码或缺陷报告中生成测试输入、测试步骤和断言的能力。一些工作关注模型微调以提升测试用例生成质量，一些工作关注基于需求的测试用例生成能力评估。该方向的核心挑战在于生成内容的可靠性和需求一致性。

第二，检索增强生成在软件工程中的应用。RAG 通过外部知识检索增强生成过程，可以缓解模型上下文不足和幻觉问题。在测试生成任务中，检索内容可能包括需求文档、接口说明、已有测试样例、报错日志和代码片段。相较于直接提示模型生成，RAG 能够将生成过程约束在可追溯的上下文之内。

第三，多智能体软件工程。MetaGPT、ChatDev、AgentCoder 等多智能体框架表明，将复杂任务拆分给不同角色智能体可以提升任务组织能力。在测试生成场景下，多智能体可分别承担需求理解、用例生成、代码生成、审计评审和错误修复等职责。与单智能体相比，多智能体方法更适合表达测试活动中“生成-评审-修正”的工作流。

第四，自动化测试自愈。传统自愈测试主要关注定位器修复、智能等待和相似元素匹配。随着大语言模型的发展，基于运行时错误信息的脚本修复成为新的方向。自愈机制的关键在于错误分类是否准确、修复策略是否可靠，以及修复后是否经过再次执行验证。

综合来看，现有研究虽已分别探索 LLM 测试生成、RAG、多智能体和自愈技术，但仍存在需求对齐不足、缺乏闭环验证、实验原型割裂等问题。本文尝试将上述技术组合为一个可执行流程，并围绕需求覆盖率、幻觉率和自愈成功情况进行实验评价。

### 1.3 研究内容与创新点

本文主要研究内容如下。

1. 设计面向需求文档的语义切片与检索模块。系统解析 Markdown 格式需求文档，将需求拆分为具有业务含义的语义片段，并支持按模块检索，为后续用例生成提供上下文。

2. 构建 Creator-Auditor 多智能体协同机制。Creator 根据检索到的需求片段生成结构化测试用例，Auditor 从一致性和完备性两个维度评审结果，减少需求幻觉和场景遗漏。

3. 实现结构化测试用例到自动化脚本的生成。系统基于 Page Object Model 生成页面对象和 Pytest 测试脚本，并使用 Playwright 执行浏览器端到端测试。

4. 设计执行反馈驱动的自愈模块。系统通过 SandboxExecutor 执行测试脚本，通过 ErrorDiagnoser 识别错误类型，并由 HealingAgent 根据错误类别选择修复策略，形成闭环。
5. 设计面向执行反馈效率的测试用例优先级排序算法。系统综合需求覆盖、风险等级、历史失败率、边界值标记和执行成本，对生成用例进行执行前排序。

本文的创新点主要体现在以下三个方面。

第一，提出面向需求对齐的 Creator-Auditor 测试用例生成机制。相比单次生成，该机制将生成与审计分离，通过角色协同提高测试用例与原始需求的一致性。

第二，构建需求驱动的测试生成闭环。框架不仅生成文本用例，还进一步生成可执行脚本并运行验证，使测试生成结果不止停留在“看起来合理”的层面。

第三，引入基于错误诊断的脚本自愈机制。系统将运行失败信息转化为错误类别和修复建议，并对定位器类问题进行策略化修复，提高脚本面对页面变化时的可维护性。

第四，引入强化学习与在线策略选择算法优化多智能体协作流程。本文将 Creator-Auditor 博弈终止过程建模为马尔可夫决策过程，设计 RL-AGS 自适应博弈终止策略，并采用 PPO 算法学习“继续迭代”与“接受输出”之间的决策边界；同时，将自愈策略选择建模为多臂赌博机问题，设计 RL-HSS 策略选择机制，根据历史修复反馈动态选择定位器修复、超时修复或大模型重写等策略。

第五，提出 RCP-TCP 测试用例优先级排序算法。该算法综合需求覆盖、风险等级、历史失败率、边界值标记和执行成本，对生成测试用例进行排序，使高风险和高收益用例更早执行，提高测试反馈效率。

## 第2章 相关技术基础

### 2.1 大语言模型与提示工程

大语言模型通过大规模文本预训练获得语言理解和生成能力，在代码生成、需求分析、测试设计等任务中具有较强适应性。测试生成任务对模型提出了更高要求：模型不仅要理解自然语言需求，还要识别前置条件、操作步骤、预期结果和异常路径。提示工程通过角色设定、输出格式约束、示例引导和任务分解，可以提升模型输出的稳定性。

在本文框架中，大语言模型主要服务于三类任务：测试用例生成、测试用例审计和脚本修复。为了降低模型不可控性，系统对输出格式进行结构化约束，并在缺少外部模型服务时提供规则化降级逻辑，保证实验流程可复现。

### 2.2 检索增强生成

检索增强生成由索引、检索和生成三个阶段组成。首先，系统将外部知识文档切分并向量化；其次，根据用户查询或任务模块检索相关片段；最后，将检索结果注入生成提示，使模型在指定上下文内完成任务。

本文将 RAG 用于需求理解阶段。与固定长度切片相比，面向测试任务的语义切片更关注功能模块、操作流程和预期结果的完整性。当前项目默认使用 TF-IDF 嵌入方案以保证 Windows 环境下的确定性和可复现性，同时保留 sentence-transformers 作为可选嵌入后端。

### 2.3 多智能体协同

多智能体系统强调不同角色之间的协作与反馈。测试工作天然包含多角色特征：有人负责理解需求，有人负责编写用例，有人负责评审覆盖度，有人负责实现脚本，有人负责执行和修复。本文将该工作流抽象为 Creator、Auditor、PageAgent、TestAgent 和 HealingAgent 等角色。

Creator 负责生成测试用例，Auditor 负责评审生成结果。二者之间形成轻量级博弈：Creator 尝试覆盖更多场景，Auditor 约束其不能脱离需求。该机制的目标不是让智能体“吵架”，而是把测试工程中的评审环节显式建模。

### 2.4 强化学习与策略选择算法

强化学习关注智能体在环境交互中通过奖励信号学习最优策略。本文将多智能体用例生成中的迭代终止问题建模为马尔可夫决策过程。状态由当前迭代轮次、审计问题数量、覆盖率估计、幻觉标记和审计通过标记组成；动作包括继续迭代和接受当前输出；奖励函数综合考虑审计通过奖励、覆盖率收益、迭代成本、幻觉惩罚和超限惩罚。本文采用 PPO 算法训练 RL-AGS 策略，用于自适应决定 Creator-Auditor 博弈何时终止。

除博弈终止外，本文还将自愈策略选择建模为多臂赌博机问题。不同修复策略被视为不同策略臂，包括大模型重写、定位器规则修复、超时等待修复和回退策略。系统根据修复是否成功更新策略价值函数，并采用 ε-greedy 机制在探索和利用之间平衡。该机制记为 RL-HSS，用于降低每次失败都调用大模型重写的成本。

### 2.5 自动化测试与 Page Object Model

Pytest 是 Python 生态中常用的测试框架，支持 fixture、参数化和插件扩展。Playwright 提供浏览器自动化能力，支持页面导航、元素定位、断言和多浏览器执行。Page Object Model 是自动化测试中常见设计模式，其核心思想是将页面元素和页面操作封装为对象，测试脚本只表达业务流程，从而降低脚本与页面结构之间的耦合。

本文生成的测试脚本采用 Pytest + Playwright + POM 组合。PageAgent 生成页面对象，TestAgent 生成测试函数和断言逻辑。该设计便于后续维护，也便于将生成产物纳入持续集成流程。

## 第3章 系统设计与实现

### 3.1 总体架构

本文系统由六个主要模块组成：需求检索模块、多智能体用例生成模块、强化学习终止决策模块、代码生成模块、执行验证模块和自愈模块。整体流程如下：

1. 输入需求文档；
2. RAG 模块解析需求并构建语义索引；
3. Creator 根据需求片段生成结构化测试用例；
4. Auditor 审计用例是否与需求一致、是否覆盖关键场景；
5. RL-AGS 根据审计状态决定是否继续迭代或接受结果；
6. PageAgent 和 TestAgent 生成 POM 页面对象和 Pytest 脚本；
7. SandboxExecutor 执行生成脚本；
8. 若执行失败，ErrorDiagnoser 分类错误，HealingAgent 和 RL-HSS 选择修复策略并复测。

该架构的关键思想是闭环控制。传统生成式方法往往在生成测试代码后结束，而本文框架将执行结果作为反馈信号，使系统具备一定自我修正能力。

### 3.2 RAG 需求检索模块

需求检索模块由 DocumentParser、SemanticChunker 和 Retriever 组成。DocumentParser 负责读取需求文档并解析功能结构；SemanticChunker 负责形成语义切片并统计切片分布；Retriever 负责构建索引并按模块或查询语句返回相关需求片段。

当前实验需求包含登录、搜索、购物车和结算四个模块。端到端验证中，RAG 索引共构建 80 个语义切片。系统在生成每个模块的测试用例时，使用对应模块的全部需求片段，避免不同模块上下文混杂导致错误生成。早期实现中按模块检索默认仅返回 5 个片段，在需求扩展后会导致 Auditor 误判合法用例为幻觉；本文修正该问题，使按模块检索在评估阶段返回完整模块上下文。

### 3.3 多智能体用例生成模块

多智能体用例生成模块由 CaseCreator、CaseAuditor 和 Coordinator 实现。CaseCreator 接收需求片段和模块名称，生成包含 test_id、module、requirement、title、precondition、steps、expected 和 type 字段的结构化用例。CaseAuditor 对生成用例进行审计，输出是否通过、问题列表和审计摘要。Coordinator 负责组织多轮迭代。

本研究中，用例类型分为正向、逆向和边界值三类。正向用例验证正常业务流程，逆向用例验证非法输入或异常状态，边界值用例验证空输入、空购物车、缺失地址等临界场景。该分类可提升测试集对真实业务风险的覆盖能力。

### 3.4 RL-AGS 自适应博弈终止算法

在固定轮次的多智能体博弈中，系统通常需要预设最大迭代次数。当第一轮结果已经满足审计要求时，继续迭代会造成额外成本；当审计仍存在明显问题时，过早停止又会降低用例质量。因此，本文设计 RL-AGS 算法，将博弈终止决策交给强化学习策略。

RL-AGS 的状态向量定义为：

```text
s = [i / Imax, n_issue / 10, c, h, p]
```

其中，`i` 表示当前迭代轮次，`Imax` 表示最大迭代轮次，`n_issue` 表示审计问题数，`c` 表示覆盖率估计，`h` 表示是否存在幻觉问题，`p` 表示审计是否通过。动作空间为：

```text
a = 0：继续迭代
a = 1：接受当前输出并终止
```

奖励函数由以下部分组成：审计通过奖励、覆盖率收益、单轮迭代惩罚、幻觉惩罚和强制退出惩罚。通过该设计，策略倾向于在审计通过且覆盖率较高时尽早停止，在存在幻觉或覆盖不足时继续迭代。

为避免强化学习策略在高风险状态下错误接受结果，本文进一步设计 Safety-gated RL-AGS 安全门控机制。其规则为：若 Auditor 输出中存在 `severity=error` 的问题，则无论 PPO 策略输出何种动作，系统均不允许接受当前结果，必须继续迭代或交由人工确认。该约束将符号审计规则与学习型策略结合，降低单纯策略模型误判带来的质量风险。

算法流程如下：

```text
Algorithm 1 Safety-gated RL-AGS
Input: audit_result, coverage_estimate, iteration
Output: stop_or_continue

1. if audit_result contains error-level issue:
2.     return CONTINUE
3. construct state s = [i/Imax, n_issue/10, c, h, p]
4. action = PPO.predict(s)
5. if action == ACCEPT:
6.     return STOP
7. else:
8.     return CONTINUE
```

### 3.5 自动化脚本生成模块

代码生成模块由 PageAgent 和 TestAgent 构成。PageAgent 生成页面对象，例如登录页、首页和购物车页等；TestAgent 根据测试用例生成测试脚本。生成脚本包含模块级测试函数、Pytest 标记和 Playwright 断言。

在当前项目中，生成产物包括 page_login.py、page_index.py、page_cart.py 以及 test_login.py、test_search.py、test_cart.py、test_checkout.py。测试脚本覆盖登录、搜索、购物车和结算四类业务流程，能够在本地 Flask 电商系统上执行。

### 3.6 执行自愈模块

自愈模块包含 SandboxExecutor、ErrorDiagnoser 和 HealingAgent。SandboxExecutor 使用 Pytest 子进程执行脚本并捕获输出；ErrorDiagnoser 根据 stdout 和 stderr 识别错误类型，包括 locator、assertion、timeout、syntax、attribute 和 import 等；HealingAgent 根据错误类型选择修复策略。

本文重点验证定位器类错误的自愈能力。在 Playwright 中，过宽泛的定位器可能触发 strict mode 冲突，即一个定位器匹配多个元素，导致点击操作失败。系统通过识别 “waiting for locator”“Locator”“get_by_role”等错误特征，将其归类为 locator 错误，并采用规则化策略将宽泛 CSS 定位器替换为语义化角色定位器。

### 3.7 RL-HSS 自愈策略选择算法

脚本自愈并不总是适合直接调用大语言模型重写。对于定位器失效、等待超时等常见错误，规则化修复通常成本更低且稳定性更高。本文将自愈策略选择建模为多臂赌博机问题，并设计 RL-HSS 算法。

设错误类别为上下文 `e`，修复策略集合为：

```text
A = {llm_rewrite, rule_locator, rule_timeout, fallback}
```

当系统选择策略 `a` 并完成修复验证后，根据修复结果给出奖励：

```text
r = 1.0   修复成功
r = -0.5  修复失败
```

策略价值按增量公式更新：

```text
Q_new(e,a) = Q_old(e,a) + alpha * (r - Q_old(e,a))
```

策略选择采用 ε-greedy 方法：以 ε 概率随机探索，以 `1-ε` 概率选择当前 Q 值最高的策略。通过该机制，系统能够在多次修复任务中逐渐偏向对特定错误类型更有效的修复策略。

## 第4章 核心算法设计

本章对系统中的核心算法进行集中描述。与单纯的工程流水线不同，本文将需求驱动测试生成过程抽象为三个可优化的决策问题：第一，如何从需求文档中提取可追溯的测试语义单元；第二，如何在 Creator-Auditor 多轮协作中决定继续迭代或接受结果；第三，如何在脚本执行失败后选择成本更低、成功率更高的修复策略。围绕上述问题，本文设计语义切片与检索算法、Safety-gated RL-AGS 自适应终止算法、RL-HSS 自愈策略选择算法和 RCP-TCP 测试用例优先级排序算法。

### 4.1 问题定义

设需求文档集合为：

```text
D = {d1, d2, ..., dn}
```

系统目标是生成测试用例集合：

```text
T = {t1, t2, ..., tm}
```

并进一步生成可执行自动化脚本集合：

```text
S = {s1, s2, ..., sk}
```

本文优化目标并不是单一最大化用例数量，而是在需求覆盖率、幻觉率、执行通过率、修复成本和迭代成本之间取得平衡。综合目标函数可表示为：

```text
max J = alpha * Coverage(T, D)
        - beta * Hallucination(T, D)
        + gamma * PassRate(S)
        - lambda * Cost
```

其中，`Coverage(T, D)` 表示生成用例对需求集合的覆盖程度，`Hallucination(T, D)` 表示用例脱离需求依据的比例，`PassRate(S)` 表示生成脚本执行通过率，`Cost` 综合表示大模型调用、迭代轮次和修复耗时。该目标函数解释了本文为什么不能只追求“多生成一些用例”：如果用例数量增加但幻觉率同步升高，系统质量反而下降。

### 4.2 需求语义切片与检索算法

需求文档通常包含功能说明、前置条件、操作步骤、异常约束和预期结果。若采用固定长度切片，容易将“操作”和“预期”切断，导致后续生成缺少依据。因此，本文采用面向测试任务的语义切片方法，将需求片段组织为“功能模块-操作路径-预期结果”结构。

算法输入为需求文档集合 `D`，输出为语义片段集合 `C`。每个片段定义为：

```text
c_i = <module, operation, precondition, expected, constraints>
```

检索阶段根据目标模块 `q` 计算查询与片段之间的相似度：

```text
sim(q, c_i) = cosine(E(q), E(c_i))
```

其中 `E(.)` 表示文本向量化函数。当前项目为保证本地可复现，默认采用 TF-IDF 表示，同时保留 sentence-transformers 作为可选语义嵌入后端。实验中完整模块上下文优于 Top-5 截断检索，说明测试生成任务中“上下文完整性”比单纯相似度排序更关键。

算法流程如下：

```text
Algorithm 1 Requirement Semantic Chunking and Retrieval
Input: requirement documents D, query module q
Output: retrieved requirement chunks Cq

1. parse D into module-level requirement blocks
2. for each block:
3.     extract operation, precondition, expected result and constraints
4.     construct semantic chunk c_i
5. build index over all chunks C
6. retrieve chunks by module q
7. if evaluation mode is enabled:
8.     return all chunks belonging to q
9. else:
10.    return top-k chunks ranked by sim(q, c_i)
```

### 4.3 Creator-Auditor 协同审计算法

Creator-Auditor 机制将测试生成拆分为生成与审计两个角色。Creator 负责根据检索上下文生成正向、逆向和边界值测试用例；Auditor 负责检查用例是否存在幻觉、遗漏、冲突和不完整描述。该机制的核心不是让多个智能体形式化“聊天”，而是把测试工程中的评审过程算法化。

设第 `r` 轮生成结果为 `T_r`，审计结果为：

```text
A_r = <passed_r, issues_r, severity_r>
```

若 `passed_r = true`，系统可接受当前测试集；若存在 error 级问题，则进入下一轮修正。多轮协作流程如下：

```text
Algorithm 2 Creator-Auditor Collaborative Test Generation
Input: requirement chunks Cq, max iteration Imax
Output: approved test cases T

1. T_0 = empty
2. for r = 1 to Imax:
3.     if r == 1:
4.         T_r = Creator(Cq)
5.     else:
6.         T_r = Creator(Cq, T_{r-1}, issues_{r-1})
7.     A_r = Auditor(T_r, Cq)
8.     if A_r.passed:
9.         return T_r
10.    decision = RL_AGS(A_r, r)
11.    if decision == ACCEPT:
12.        return T_r
13. return T_Imax
```

该算法为 RL-AGS 提供可观测状态，也为实验消融提供明确对照：关闭 Auditor 时，系统退化为单次生成；关闭 RAG 时，Auditor 缺少需求依据，幻觉识别会显著恶化。

### 4.4 Safety-gated RL-AGS 自适应终止算法

固定轮次策略存在天然缺陷：轮次过少时无法充分修正错误，轮次过多时浪费大模型调用成本。本文将 Creator-Auditor 迭代终止问题建模为马尔可夫决策过程：

```text
M = <S, A, P, R, gamma>
```

状态空间 `S` 由五维观测向量构成：

```text
s_r = [
  r / Imax,
  |issues_r| / 10,
  coverage_r,
  hallucination_flag_r,
  audit_passed_flag_r
]
```

动作空间为：

```text
A = {CONTINUE, ACCEPT}
```

奖励函数设计为：

```text
R(s_r, a_r) =
  R_pass * audit_passed
  + R_cov * coverage_gain
  - C_iter
  - P_hal * hallucination_flag
  - P_force * force_exit_flag
```

其中，审计通过和覆盖率提升带来正奖励，迭代成本、幻觉问题和超限退出带来惩罚。本文采用 PPO 训练策略网络，使其学习在质量收益和调用成本之间进行权衡。

仅依赖学习策略存在风险：当训练样本不足或状态分布偏移时，PPO 可能在高风险状态下错误输出 `ACCEPT`。因此本文进一步加入安全门控：

```text
if exists issue in issues_r where issue.severity == error:
    action = CONTINUE
else:
    action = PPO(s_r)
```

完整流程如下：

```text
Algorithm 3 Safety-gated RL-AGS
Input: audit result A_r, coverage estimate coverage_r, iteration r
Output: stop decision

1. if A_r contains error-level issue:
2.     return CONTINUE
3. construct state s_r
4. action = PPO.predict(s_r)
5. if action == ACCEPT:
6.     return STOP
7. return CONTINUE
```

该算法体现了本文的一个关键原则：测试生成属于质量敏感任务，学习型策略不能无约束接管最终质量判断。Safety Gate 将符号规则与强化学习结合，避免模型在明显错误状态下提前终止。

### 4.5 RL-HSS 自愈策略选择算法

脚本执行失败后，不同错误类型适合不同修复策略。例如，定位器冲突通常优先使用规则化定位器替换；等待超时适合调整等待策略；复杂语法或逻辑错误才需要调用大模型重写。若所有错误都直接交给大模型，成本高且不稳定。因此本文将自愈策略选择建模为多臂赌博机问题。

对每一种错误类型 `e`，策略集合定义为：

```text
A_e = {llm_rewrite, rule_locator, rule_timeout, fallback}
```

策略价值函数为：

```text
Q(e, a) = E[r | e, a]
```

执行修复后，根据复测结果返回奖励：

```text
r = 1.0   if repair succeeds
r = -0.5  if repair fails
```

Q 值更新公式为：

```text
Q_new(e,a) = Q_old(e,a) + alpha * (r - Q_old(e,a))
```

策略选择采用 ε-greedy：

```text
a =
  random(A_e),               with probability epsilon
  argmax_a Q(e,a),           with probability 1 - epsilon
```

后续可将当前 ε-greedy 扩展为 Contextual Bandit，引入错误日志长度、DOM 变化程度、失败次数、历史成功率和修复耗时等上下文特征，使策略选择从“按错误类型记忆”升级为“按错误状态决策”。

### 4.6 RCP-TCP 测试用例优先级排序算法

当系统生成大量测试用例后，执行顺序会影响缺陷暴露速度和持续集成反馈效率。本文新增 RCP-TCP 算法，在执行前对测试用例进行排序，使高风险、高覆盖、历史失败率高且执行成本可控的用例优先运行。

对测试用例 `t`，优先级得分定义为：

```text
Score(t) =
  w1 * RequirementCoverage(t)
  + w2 * RiskLevel(t)
  + w3 * HistoricalFailureRate(t)
  + w4 * BoundaryCaseFlag(t)
  - w5 * ExecutionCost(t)
```

其中，`RequirementCoverage(t)` 表示用例关联需求的重要程度，`RiskLevel(t)` 根据正向、逆向和边界值类型赋值，`HistoricalFailureRate(t)` 表示历史失败比例，`BoundaryCaseFlag(t)` 用于提高边界用例权重，`ExecutionCost(t)` 用于惩罚耗时较长的用例。

算法流程如下：

```text
Algorithm 4 RCP-TCP Test Case Prioritization
Input: generated test cases T, requirement chunks C, history H
Output: ranked test cases T'

1. for each test case t in T:
2.     compute RequirementCoverage(t, C)
3.     compute RiskLevel(t)
4.     compute HistoricalFailureRate(t, H)
5.     compute BoundaryCaseFlag(t)
6.     estimate ExecutionCost(t)
7.     Score(t) = weighted sum of the above features
8. sort T by Score(t) in descending order
9. return ranked list T'
```

该算法的价值在于补齐“生成之后如何执行”的决策问题。对于毕业论文而言，它也提供了一个清晰、可复现、易实验对比的算法点，可与无排序、按模块排序、按风险排序等基线进行对比。

### 4.7 算法复杂度分析

设需求片段数为 `n`，生成用例数为 `m`，最大迭代轮次为 `Imax`，修复策略数为 `k`。语义检索在 TF-IDF 表示下主要开销来自向量相似度计算，单次查询复杂度约为 `O(n)`；Creator-Auditor 协同最多执行 `Imax` 轮，若每轮审计 `m` 条用例，则审计侧复杂度约为 `O(Imax * m)`；RL-AGS 推理仅需一次策略网络前向计算，相对 LLM 调用成本可以忽略；RL-HSS 每次选择策略需要比较 `k` 个策略臂，复杂度为 `O(k)`；RCP-TCP 对 `m` 条用例计算分数并排序，复杂度为 `O(m log m)`。

从工程角度看，系统主要成本仍来自 LLM 生成、浏览器执行和失败复测。本文算法设计的核心目的不是制造复杂模型，而是减少无效迭代、优先执行高价值用例，并在常见错误上减少不必要的大模型调用。

### 5.3 强化学习策略实验

当前项目已集成基于 PPO 的 RL-AGS 模型，模型文件位于 `.cache/rl_models/ags_ppo.zip`。在最新 RL 模式运行中，系统加载该模型并参与 Creator-Auditor 博弈终止决策，实验报告保存为 `experiments/results/agent_pipeline_20260921_210235.json`。该报告中 `use_rl=true`，说明强化学习策略已接入主流水线。

不过，由于当前 4 个干净需求模块在第一轮即审计通过，RL-AGS 的轮次优化优势尚未充分体现。为进一步验证审计和安全决策机制，本文补充构造了包含冲突需求、模糊需求、幻觉用例和不完整用例的鲁棒性实验。实验结果显示，Auditor 能识别 ambiguous_requirement、conflicting_requirement、hallucination 和 incomplete 等问题；同时，原始 PPO 策略在高风险状态下可能输出 accept，因此本文增加 Safety-gated RL-AGS 约束：只要审计结果包含 error 级问题，RL 不允许终止，只能继续迭代或交由人工确认。

鲁棒性实验结果如下：

| 问题类型 | 识别数量 |
|---|---:|
| ambiguous_requirement | 6 |
| conflicting_requirement | 2 |
| hallucination | 2 |
| incomplete | 2 |

在该实验中，原始 PPO 输出动作为 `accept`，Safety-gated RL-AGS 将最终动作修正为 `continue`。这说明单纯依赖策略模型并不稳妥，引入审计安全门控可以避免错误需求和幻觉用例被提前接受。

为进一步比较不同终止策略，本文构造 clean_passed_generation、noisy_conflict_and_hallucination、warning_only_incomplete_description 和 hallucination_error 四类审计状态，并比较固定轮次、原始 PPO 与 Safety-gated RL-AGS 的决策结果。实验报告保存为 `experiments/results/strategy_comparison_latest.json`。

| 策略 | 平均迭代轮次 | 不安全接受数 | 不安全接受率 |
|---|---:|---:|---:|
| 固定 1 轮 | 1.0 | 2 | 50.0% |
| 固定 3 轮 | 3.0 | 2 | 50.0% |
| 固定 5 轮 | 5.0 | 2 | 50.0% |
| 原始 PPO | 1.0 | 2 | 50.0% |
| Safety-gated RL-AGS | 1.0 | 0 | 0.0% |

该结果说明，单纯增加固定迭代轮次并不能自动解决高风险结果被接受的问题，反而会增加调用成本；原始 PPO 在当前训练样本不足时也可能偏向过早接受。Safety-gated RL-AGS 通过 error 级审计约束将不安全接受率从 50.0% 降至 0.0%，因此更适合测试生成这类质量敏感场景。

### 5.4 自愈实验

为验证自愈模块，本文构造 Playwright strict mode 定位器冲突。具体做法是将组合搜索测试中的语义化按钮定位：

```python
page.get_by_role("button", name="搜索").click()
```

替换为过宽泛的 CSS 定位：

```python
page.locator("button[type='submit']").click()
```

由于页面中存在多个提交按钮，该定位器匹配多个元素，导致测试失败。自愈流程首先执行破坏后的脚本并确认失败，然后由 ErrorDiagnoser 将错误识别为 locator 类问题，HealingAgent 选择 rule_locator 策略进行修复，最后再次执行修复后的脚本。

实验结果如下：

| 阶段 | 结果 |
|---|---|
| 故障类型 | Playwright strict mode locator conflict |
| 修复前执行 | failed |
| 诊断类别 | locator |
| 修复策略 | rule_locator |
| 修复尝试次数 | 1 |
| 修复后执行 | passed |

该实验表明，自愈模块能够处理典型定位器失效问题。但需要指出的是，当前自愈能力仍主要覆盖规则明确的常见故障，对复杂业务逻辑错误、跨页面状态错误和需求本身变更导致的断言错误仍需进一步扩展。

### 5.5 消融实验

为进一步分析各模块对系统效果的影响，本文设计了三组可复现实验：RAG 上下文消融、Auditor 消融和 Safety Gate 消融。实验报告保存为 `experiments/results/ablation_suite_20260921_220413.json`，同时保留最新报告 `experiments/results/ablation_suite_latest.json`。

RAG 上下文消融用于验证需求上下文完整性对审计结果的影响。本文比较完整模块上下文、每模块仅保留前 5 个需求片段、完全不提供 RAG 上下文三种设置。结果如下：

| 设置 | 总用例数 | 总问题数 | error 数 | 幻觉问题数 | 通过模块数 |
|---|---:|---:|---:|---:|---:|
| 完整 RAG | 80 | 18 | 0 | 0 | 4 |
| 截断 RAG Top-5 | 80 | 76 | 58 | 58 | 0 |
| 无 RAG | 80 | 98 | 80 | 80 | 0 |

完整 RAG 下，Auditor 未产生 error 级问题，所有模块审计通过；18 个问题均为边界值描述不够明确的 warning。截断 RAG 和无 RAG 会导致 Auditor 无法看到完整需求依据，从而大量误判合法用例为幻觉。这说明，在需求驱动测试生成任务中，检索上下文完整性直接影响审计可信度。

Auditor 消融用于验证审计智能体在脏需求场景中的作用。本文构造包含模糊需求、冲突需求、幻觉用例和不完整用例的数据集。无 Auditor 时，系统会直接接受 4 条已知问题用例；启用 Auditor 后，系统识别出 12 个问题，其中包括 6 个模糊需求、2 个冲突需求、2 个幻觉用例和 2 个不完整问题。

Safety Gate 消融用于验证 Safety-gated RL-AGS 的必要性。在脏需求状态下，原始 PPO 策略输出 `accept`，存在提前接受高风险结果的风险；加入 Safety Gate 后，由于审计结果包含 error 级问题，最终动作被修正为 `continue`。该结果表明，强化学习策略需要与规则审计约束结合使用，才能满足测试生成任务对可靠性的要求。

### 5.6 测试用例优先级排序实验

为验证 RCP-TCP 测试用例优先级排序算法，本文基于最新端到端生成报告提取 80 条测试用例，并按照需求覆盖特征、风险级别、历史失败率、边界值标记和执行成本计算优先级分数。排序结果保存为 `experiments/results/prioritization_latest.json`，策略对比结果保存为 `experiments/results/strategy_comparison_latest.json`。

该实验的主要作用不是证明排序会改变最终覆盖率，而是验证在相同测试集合下，高风险、边界类和历史失败用例能否被提前执行。本文将前 20% 执行队列作为观察窗口，并统计高风险用例捕获率、边界值用例捕获率和历史失败用例捕获率。历史失败样本来自自愈实验中的 `TC-SEARCH-005`，该用例曾因 Playwright strict mode 定位器冲突失败，并由自愈模块修复。

可对比的基线包括：

| 策略 | 说明 |
|---|---|
| 无排序 | 按生成顺序执行 |
| 模块顺序排序 | 按 login、search、cart、checkout 固定顺序执行 |
| 风险排序 | 仅根据用例类型排序 |
| RCP-TCP | 综合覆盖、风险、历史失败率、边界标记和执行成本排序 |

实验结果如下：

| 策略 | 前 20% 高风险捕获率 | 前 20% 边界值捕获率 | 前 20% 历史失败捕获率 |
|---|---:|---:|---:|
| 无排序 | 34.38% | 27.78% | 0.0% |
| 模块顺序排序 | 12.50% | 16.67% | 0.0% |
| 风险排序 | 50.00% | 88.89% | 0.0% |
| RCP-TCP | 46.88% | 83.33% | 100.0% |

从结果看，风险排序能够最大化边界值用例的前置比例，但无法利用历史失败反馈；RCP-TCP 在保持较高风险用例捕获率的同时，将已知历史失败用例提升到前 20% 执行队列，说明其能够把执行反馈纳入排序决策。该结果也说明，排序算法不是简单把“边界值”排最前，而是在风险、历史失败和成本之间做权衡。

### 5.7 结果讨论

实验结果初步证明了本文方法的可行性。RAG 模块为用例生成提供可追溯需求上下文，Creator-Auditor 机制降低了幻觉风险，Safety-gated RL-AGS 在存在 error 级问题时提供了安全约束，POM 代码生成使测试脚本具备一定结构化质量，自愈模块则为脚本维护提供了闭环能力。

不过，当前实验仍有局限。第一，被测系统规模较小，实验场景集中在电商基础流程，尚不能代表大型工业系统。第二，覆盖率和幻觉率依赖当前 ground truth 标注，后续需要引入更多人工标注样本提高评价稳健性。第三，自愈实验目前主要验证定位器冲突，后续应扩展为超时、断言变化、状态污染和接口变更等多类型故障集。第四，当前默认嵌入后端为 TF-IDF，虽然可复现性强，但语义表达能力弱于专用句向量模型。第五，PPO 策略训练环境仍带有模拟成分，后续应采集更多真实审计轨迹进行训练和评估。

## 第6章 总结与展望

本文围绕需求驱动自动化测试生成问题，设计并实现了一种基于多智能体协同的测试生成与自愈框架。系统通过 RAG 对需求文档进行语义检索，通过 Creator-Auditor 机制生成并审计测试用例，通过 PageAgent 和 TestAgent 生成可执行 Playwright 测试脚本，并通过执行反馈驱动的自愈模块修复定位器类故障。

实验结果显示，在本地 Flask 电商系统上，框架能够生成 80 条端到端测试用例，需求覆盖率达到 100.0%，幻觉率为 0.0%，生成测试套件全部执行通过，Pytest 结果为 80 passed。自愈实验中，系统能够识别并修复 Playwright 定位器冲突，修复后脚本执行成功。鲁棒性实验进一步表明，系统可以识别模糊需求、冲突需求、幻觉用例和不完整用例，并通过 Safety-gated RL-AGS 阻止高风险用例集被错误接受。

未来工作可从以下方向展开：第一，扩展被测系统规模，引入真实开源电商系统或企业级业务系统进行验证；第二，扩展更多消融实验组，例如不同嵌入模型、不同审计阈值、不同故障类型下的对比；第三，扩展错误诊断与修复策略，覆盖断言错误、等待超时、状态污染和接口变更等更多场景；第四，引入更强语义嵌入模型并比较其对检索质量和生成质量的影响；第五，完善论文实验统计，进行多次重复实验并报告均值、方差和失败案例。
