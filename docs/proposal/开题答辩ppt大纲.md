## 3. 研究背景

- 软件系统迭代频繁，自动化测试需求持续增长。
- 传统测试用例设计依赖人工理解需求、拆分场景、编写脚本，成本高、效率低。
- 大语言模型具备需求理解、测试用例生成和代码生成能力，为自动化测试生成提供新路径。
- 但 LLM 直接生成测试仍存在幻觉、遗漏、不可执行和维护成本高等问题。

建议图示：

- “需求文档 → 人工测试设计 → 自动化脚本”的传统流程图。
- 标注人工成本高、质量依赖经验、维护困难。

---

## 4. 核心问题

本研究主要解决四个问题：

- 需求理解问题：LLM 容易遗漏业务规则、边界条件和异常路径。
- 幻觉问题：模型可能编造不存在的页面元素、接口、流程或断言。
- 固定迭代问题：多智能体审计如果采用固定轮次，简单任务浪费成本，复杂任务又可能提前停止。
- 脚本维护问题：生成的 Web 自动化脚本容易因定位器变化、等待超时、断言变化而失败。

这一页要讲狠一点：LLM 不是测试工程师，直接让它生成测试，很多时候就是“看起来挺像那么回事，跑起来一地鸡毛”。

---

## 5. 国内外研究现状

可以分四类讲：

- LLM 测试用例生成：已有研究证明 LLM 可用于测试用例生成，但直接生成质量不稳定。
- RAG 测试生成：检索增强能补充需求上下文，减少遗漏，但不能独立解决审计和执行反馈问题。
- 多智能体测试生成：多 Agent 共识和审计机制可降低幻觉，但常采用固定轮次迭代。
- 强化学习与自愈测试：RL 可用于测试脚本自愈或策略选择，但与需求驱动测试生成结合仍不充分。

建议引用：

- Cao et al., 2025：LLM 测试用例生成微调。
- Luo et al., 2025：组件化工业软件测试生成。
- Xu et al., 2025：多智能体 JUnit 测试生成。
- Shin et al., 2024：RAG 测试生成。
- Gahlot et al., 2024：PPO 与 Playwright 自愈测试。

## 6. 研究空白

现有方法的不足：

- 只用 LLM：生成快，但幻觉和遗漏严重。
- LLM + RAG：有需求上下文，但缺少独立审计。
- 多智能体审计：能提升质量，但固定轮次策略僵硬。
- 自愈测试：多关注脚本修复，较少与测试生成全过程闭环结合。

本文切入点：

- 构建“RAG + 多智能体审计 + 强化学习决策 + 执行反馈验证”的闭环测试生成研究框架。

## 7. 研究目标与研究内容

研究目标：

- 面向 LLM 自动化测试生成中的需求遗漏、幻觉生成、固定迭代和脚本失效问题，构建可检索、可审计、可决策、可执行验证的测试生成方法。

- 通过 Spree Commerce 开源电商平台上的对比实验和消融实验，验证本文方法在需求覆盖率、幻觉率、脚本通过率和生成成本方面的有效性。

研究内容：

- 研究内容一：需求驱动的 RAG 检索增强测试生成方法。
- 研究内容二：面向需求一致性的 Creator-Auditor 多智能体审计机制。
- 研究内容三：基于 PPO 的 RL-AGS 自适应生成审计决策方法。
- 研究内容四：执行反馈驱动的测试脚本有效性验证与修复机制。

## 10. 研究内容一：RAG 需求检索增强

输入：

- Spree Commerce 需求文档
- 商品、搜索、购物车、结算、账户等模块需求

处理：

- 需求解析
- 语义切片
- 向量化存储
- Top-K 相关需求召回

作用：

- 给 LLM 提供真实需求依据。
- 降低模型凭空生成。
- 提升边界场景和异常场景覆盖。

学术定位：

- 研究 RAG 对需求覆盖和幻觉率的影响，而不是单纯介绍向量库或代码实现。

---

## 11. 研究内容二：Creator-Auditor 多智能体审计机制

智能体角色：

- Creator Agent：生成正向、逆向、边界测试用例。
- Auditor Agent：检查需求一致性、覆盖完整性、断言合理性、可执行性。
- Coordinator：调度流程并记录状态。

核心逻辑：

- 生成不是一次完成，而是经过审计和反馈迭代。
- Auditor 的作用是把 LLM 输出从“像测试”拉回“符合需求的测试”。

学术定位：

- 重点分析多智能体审计机制对需求一致性、覆盖完整性和幻觉控制的作用。
- 页面对象、脚本生成等工程细节不作为主要贡献，只作为实验执行支撑。

---

## 12. 研究内容三：强化学习策略 RL-AGS

研究重点：

- 将 Creator-Auditor 迭代过程建模为马尔可夫决策过程。
- 使用 PPO 学习动态决策策略。

状态空间：

- 当前迭代轮次
- 审计问题数量
- 严重问题数量
- 需求覆盖率
- 幻觉率
- 覆盖率提升幅度
- 脚本执行通过率
- 累计 LLM 调用成本

动作空间：

- 继续当前生成审计迭代
- 接受当前结果并停止
- 切换生成策略

奖励函数：

- 覆盖率提升：正奖励
- 审计通过：正奖励
- 脚本通过率提升：正奖励
- 幻觉内容：负奖励
- 严重审计问题：负奖励
- LLM 调用成本：负奖励

一句话讲法：

- RL-AGS 的目标不是让模型“更会写测试”，而是让系统学会“什么时候该继续改，什么时候该停，什么时候该换策略”。

学术定位：

- 本文核心创新点是将生成审计迭代过程建模为序贯决策问题，并通过 PPO 学习自适应终止和策略切换机制。

---

## 13. 研究内容四：执行反馈验证与自愈

研究重点：

- 将生成结果从文本质量评价推进到可执行性评价。
- 通过执行日志识别脚本失败原因。
- 分析失败修复策略对最终脚本通过率和修复成本的影响。

常见失败类型：

- 定位器失效
- 等待超时
- 断言失败
- 测试数据异常
- 环境或服务异常

修复策略：

- 规则修复
- 候选定位器替换
- 等待策略调整
- 断言重写
- LLM 局部修复
- 回退策略

评价指标：

- 自愈成功率
- 修复后脚本通过率
- 平均修复次数
- 修复成本

学术定位：

- 自愈机制不是论文主创新，而是将测试生成结果纳入执行反馈闭环，用于增强实验验证完整性。

## 16. 评价指标与检测方法

核心原则：

- 指标不是主观拍脑袋，而是来自需求映射、脚本执行日志、错误修复记录和对比实验统计。
- 需求类指标基于 Spree ground truth。
- 执行类指标由 Pytest/Playwright 自动判定。
- LLM 质量类指标先由规则和 Auditor 判断，再进行抽样人工复核。

| 指标 | 检测方法 | 计算方式 |
|---|---|---|
| 需求覆盖率 | 将 Spree 需求拆分为编号需求点，例如 `REQ-CART-001`，检查生成测试是否覆盖对应需求 | 覆盖需求数 / 总需求数 |
| 幻觉率 | 检查测试中是否出现需求文档和系统页面中不存在的功能、按钮、字段、流程或断言 | 幻觉测试数 / 生成测试总数 |
| 测试脚本通过率 | 运行生成的 Playwright/Pytest 脚本，读取测试执行结果 | 通过脚本数 / 总脚本数 |
| 自愈成功率 | 对失败脚本执行自愈修复，修复后重新运行；原失败脚本变为通过则记为成功 | 修复后通过的失败脚本数 / 尝试自愈的失败脚本数 |
| 平均迭代轮次 | 记录每个需求从生成到审计通过所经历的 Creator-Auditor 轮次 | 总迭代轮次 / 需求任务数 |
| LLM 调用成本 | 记录每次模型调用次数、输入输出 token 或估算费用 | 总调用次数、总 token 或总费用 |
| 审计通过率 | Auditor 判断测试用例是否满足需求一致性、覆盖完整性、断言合理性和可执行性 | 审计通过用例数 / 审计用例总数 |
| 修复成本 | 记录每个失败脚本的修复次数、修复耗时和 LLM 调用消耗 | 平均修复次数 / 平均修复耗时 / 平均 token |

自愈成功率示例：

```text
第一次执行：生成 20 条测试脚本，其中 12 条通过，8 条失败。
自愈模块处理 8 条失败脚本，其中 5 条修复后通过，3 条仍失败。

初始脚本通过率 = 12 / 20 = 60%
自愈成功率 = 5 / 8 = 62.5%
最终脚本通过率 = (12 + 5) / 20 = 85%
```
