## 第 2 页：研究问题与目标

**核心问题：** 单次依赖 LLM 生成自动化测试，容易出现需求遗漏、内容幻觉、脚本不可执行和失效后无法恢复。

**项目目标：**

- 从自然语言需求自动生成结构化测试用例与可执行脚本。
- 通过 Creator–Auditor 协作降低遗漏和幻觉。
- 通过强化学习控制协作迭代与自愈策略选择。
- 在脚本失效后完成诊断、修复和回归验证，形成闭环。

**本页结论：** 研究对象不是一个“会写测试代码的聊天机器人”，而是一套可验证、可反馈、可自愈的测试生成系统。

## 第 3 页：系统总体架构

建议绘制六层架构图：

```text
Markdown 需求文档
        ↓
语义切片与 RAG 检索
        ↓
Creator 生成 ←→ Auditor 审计
        ↓          ↑
  RL-AGS 动态决策 / Safety Gate
        ↓
PageAgent + TestAgent 生成 POM / Pytest
        ↓
Playwright 执行 → 错误诊断 → RL-HSS 策略选择 → 修复与复测
```

**已实现模块：** RAG、多智能体协作、代码生成、强化学习决策、自愈、实验评估、被测电商系统。

**本页结论：** 当前已形成“需求—生成—审计—执行—修复”的完整闭环。

## 第 5 页：已完成二——Creator–Auditor 多智能体协作

| 角色 | 已实现职责 |

| Creator Agent | 基于检索上下文生成正向、逆向和边界测试用例 |

**已实现机制：**

- 对“模糊需求、冲突需求、无依据用例、步骤/预期缺失”进行识别。

**本页结论：** 将一次性生成改造成可审计的协作过程，质量控制被显式纳入主链路。

## 第 6 页：已完成三——强化学习决策与安全门控

**RL-AGS / PPO：**

- 根据迭代轮次、问题数量、覆盖估计和幻觉状态决定继续或接受。
- 已接入主流程；最新端到端报告中 `use_rl=true`。

**Safety Gate：**

- 当存在高风险审计错误时，覆盖 PPO 的不安全“接受”动作。
- 防止策略模型在脏需求场景中提前终止。

**RL-HSS / ε-greedy Bandit：**

- 根据历史修复收益选择自愈策略。

**建议配图：** PPO 原始动作 `accept` → 安全门判断存在错误 → 最终动作 `continue`。

**本页结论：** 强化学习负责效率优化，规则安全门负责质量底线；二者不是互相替代关系。

## 第 8 页：已完成五——执行、诊断与自愈闭环

**已实现链路：**

```text
执行测试 → 捕获日志与 Traceback → 错误分类
        → 选择修复策略 → 生成修复脚本 → 回归复测
```

**支持的主要错误类别：** locator、assertion、timeout、syntax、attribute、import。

**当前已验证案例：**

- 人为注入过宽的 CSS 定位器。
- Playwright strict mode 因匹配多个按钮而失败。
- 系统识别为 `locator` 错误。
- 使用 `rule_locator` 策略，1 次修复成功。
- 修复后的搜索测试共 7 条，全部通过。

**本页结论：** 自愈并非只修改文本，而是经过“失败—修复—重新执行”的闭环验证。

## 第 11 页：消融实验——RAG 与 Auditor 的贡献

### RAG 上下文消融

| 设置 | 总问题数 | 错误级问题 | 幻觉问题 | 通过模块 |
|---|---:|---:|---:|---:|
| 完整 RAG | 18 | 0 | 0 | 4 |
| 截断 RAG Top-5 | 76 | 58 | 58 | 0 |
| 无 RAG | 98 | 80 | 80 | 0 |

### Auditor 消融

- 启用 Auditor：在脏数据中检出 12 个问题，拒绝通过。
- 不启用 Auditor：4 个已知坏用例全部被接受，问题检出数为 0。

**本页结论：** RAG 提供需求依据，Auditor 提供质量闸门；缺任何一个，生成结果都可能“看起来像样，实际上胡来”。

**严谨备注：** 完整 RAG 下仍有 18 个 warning，不能表述为“完全无问题”；准确说法是“无错误级问题、无幻觉，四模块通过”。

## 第 13 页：阶段性成果与当前边界

### 已经完成

- 完整工程框架与命令行入口。
- RAG 需求解析、检索和降级机制。
- Creator–Auditor 生成审计协作。
- RL-AGS、Safety Gate 与 RL-HSS 算法接入。
- POM + Pytest + Playwright 代码生成。
- 错误诊断、自愈与回归验证。
- 80 条用例端到端验证、消融实验和脏需求实验。

### 当前边界

- 主实验仍集中于单一 Flask 电商系统，外部有效性有限。
- 自愈的完整验证目前主要是定位器故障，故障类型覆盖还不够。
- 现有结果以单次实验为主，缺少多次重复的均值、方差和显著性分析。
- “100% 覆盖率”是相对于当前 Ground Truth 的需求覆盖，不等价于真实缺陷发现率 100%。

**本页价值：** 主动划清结论边界，避免把阶段性结果吹成普适结论。

## 第 14 页：下一步计划与总结

**下一步优先级：**

1. 扩展故障注入集：定位器缺失、断言变化、超时、依赖导入、页面状态污染。
2. 每组实验至少重复 5 次，报告均值、标准差与置信区间。
3. 增加 LLM Only、RAG Only、固定轮次与 RL 决策的统一成本—质量对比。
4. 在主实验稳定后迁移到 Spree / `my-store`，验证跨系统泛化能力。
5. 增加真实缺陷或变异测试，补足“测试通过率不等于缺陷检测能力”的证据缺口。

**总结句：**

> 当前已经完成一套可运行、可审计、可执行、可自愈的需求驱动测试智能体原型；现阶段的核心任务已从“搭框架”转向“扩大实验、验证泛化、做实统计证据”。

## 备份页 B：答辩时应避免的三个错误表述

1. **不要说“80 条全部通过，所以系统能发现所有缺陷”。** 通过率反映脚本可执行性，不直接代表缺陷检测能力。
2. **不要说“PPO 已证明优于固定轮次”。** 当前证据证明 Safety Gate 阻止了一次危险接受；算法优越性仍需重复对比实验。
3. **不要说“自愈能力已覆盖所有故障”。** 当前有扎实证据的是 locator 故障的一次闭环修复，其他类别仍需系统实验。
