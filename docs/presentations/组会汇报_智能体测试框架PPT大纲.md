## 3. 研究目标

本研究希望构建一个智能体自动化测试生成框架，使大语言模型不只是一次性生成测试用例，而是能够结合需求上下文，经过生成、审计、修复和动态决策，输出更可靠的自动化测试用例。

页面内容：

- 输入：需求文档、页面信息、接口信息、历史测试结果。
- 输出：结构化测试用例、自动化测试脚本、测试执行反馈。
- 目标：提高测试用例覆盖率、通过率和生成效率。

讲述重点：

- 我的研究重点不是搭建被测系统，而是构建测试生成框架。
- 电商业务场景只是实验验证对象。

## 4. 当前研究问题

当前主要解决三个问题：

| 问题 | 表现 | 对应解决方案 |
|---|---|---|
| 上下文不足 | LLM 容易遗漏需求、业务规则和页面约束 | RAG 检索增强 |
| 质量不可控 | 一次性生成的测试用例可能存在错误、遗漏和断言不合理 | Creator-Auditor-Repair 多智能体闭环 |
| 迭代策略固定 | 固定轮次会导致过度迭代或迭代不足 | PPO / DQN 动态决策 |

讲述重点：

- 这三个问题分别对应后面的三个核心模块。
- 这样讲主线会更清楚。

## 5. 总体框架设计

```text
需求文档 / 页面信息 / 接口信息
        ↓
RAG 检索增强
        ↓
Creator Agent 生成测试用例
        ↓
Auditor Agent 审计测试用例
        ↓
Repair Agent 修复问题用例
        ↓
Coordinator / RL 决策是否继续迭代
        ↓
输出并执行自动化测试用例
        ↓
收集执行结果并反馈
```

页面内容：

- RAG：提供需求和业务上下文。
- Creator：生成测试用例。
- Auditor：审查测试用例质量。
- Repair：根据审计反馈修复用例。
- RL 决策：判断是否继续迭代。
- 测试执行：运行生成的测试脚本并收集结果。

讲述重点：

- 当前已经完成 Creator-Auditor 基础链路。
- RAG、Repair、RL 是下一阶段重点增强内容。

## 10. 后续增强一：RAG 检索增强

### 10.1 为什么要做

LLM 直接生成测试用例时，容易出现：

- 需求理解不完整。
- 忽略业务规则。
- 测试步骤泛化。
- 编造不存在的页面元素或接口。

### 10.2 准备怎么做

```text
需求文档 / 页面说明 / 接口描述
        ↓
语义切片
        ↓
向量化存储
        ↓
Top-K 检索
        ↓
上下文注入 Prompt
        ↓
生成更贴合需求的测试用例
```

### 10.3 准备验证什么

- 需求覆盖率是否提升。
- 测试步骤错误是否减少。
- 幻觉内容是否减少。
- 生成结果与业务场景是否更匹配。

讲述重点：

- RAG 的作用是补上下文，不是炫技术。
- 后续实验要证明它确实提升了测试生成质量。

## 11. 后续增强二：Repair Agent 与多智能体协作

页面内容：

新增 Repair Agent 后，流程变为：

```text
Creator：生成测试用例
Auditor：发现问题
Repair：根据问题修复用例
Coordinator：控制流程
```

Repair Agent 主要修复：

- 缺失测试步骤。
- 断言不完整。
- 测试数据不合理。
- 异常场景遗漏。
- 自动化脚本语法或定位问题。

AutoGen 的作用：

- 管理多智能体协作流程。
- 规范 Agent 之间的信息传递。
- 提高框架可扩展性。

讲述重点：

- AutoGen 是工程框架，不是论文算法创新点。
- 创新重点在多智能体测试生成闭环和后续动态决策。

## 12. 后续增强三：强化学习动态决策

### 12.1 要解决的问题

固定轮次迭代存在两个问题：

- 测试用例已经合格还继续迭代，浪费 LLM 调用成本。
- 测试用例仍有问题但迭代提前结束，影响最终质量。

### 12.2 解决思路

使用强化学习模块动态决定：

- 继续迭代。
- 接受当前结果。
- 切换生成策略重新生成。

### 12.3 状态空间 State

- 当前迭代轮次。
- Auditor 发现的问题数量。
- 严重问题数量。
- 当前需求覆盖率。
- 测试执行通过率。
- 上一轮修复成功数量。
- LLM 调用成本。

### 12.4 动作空间 Action

- 继续迭代。
- 接受当前测试用例。
- 重新生成或切换 Prompt 策略。

### 12.5 奖励函数 Reward

- 覆盖率提升：正奖励。
- 测试通过率提升：正奖励。
- 审计通过：正奖励。
- 错误数量增加：负奖励。
- 调用成本增加：负奖励。
- 无效迭代：负奖励。

讲述重点：

- PPO 是后续核心算法增强。
- 当前重点是先构建可训练环境、状态空间和奖励函数。
- DQN 可作为对比算法，不要抢 PPO 主线。

## 13. 实验设计

### 13.1 对比方法

| 方法 | 目的 |
|---|---|
| LLM Only | 作为基础基线 |
| LLM + RAG | 验证检索增强是否有效 |
| Creator-Auditor | 验证审计机制是否有效 |
| Creator-Auditor-Repair | 验证修复闭环是否有效 |
| Full Framework + RL | 验证动态迭代决策是否有效 |

### 13.2 评价指标

- 测试用例通过率。
- 需求覆盖率。
- 缺陷检测率。
- 审计通过率。
- 平均迭代轮次。
- 平均生成时间。
- LLM 调用成本。
- 修复成功率。

讲述重点：

- 实验设计要服务于验证每个模块有没有用。
- 不要只做最终结果对比，要有消融实验。

## 14. 消融实验设计

| 实验 | 对比内容 | 验证目标 |
|---|---|---|
| RAG 消融 | 有 RAG vs 无 RAG | 验证上下文增强效果 |
| Auditor 消融 | 有 Auditor vs 无 Auditor | 验证审计机制效果 |
| Repair 消融 | 有 Repair vs 无 Repair | 验证自动修复效果 |
| RL 消融 | 固定轮次 vs RL 动态决策 | 验证动态决策效果 |
| 算法对比 | PPO vs DQN | 比较不同 RL 算法效果 |

讲述重点：

- 消融实验是论文说服力的关键。
- 每个模块都要通过对比实验说明价值。
