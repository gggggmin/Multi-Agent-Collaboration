### 第 3-4 页 — 研究背景与痛点（2 页）

**第 3 页：自动化测试的现状**
- 自动化测试是软件质量保障的核心，但脚本编写和维护成本高
- 当前痛点：人工理解 PRD → 手写脚本 → 需求变更→ 大量脚本维护
- 数据：企业自动化测试脚本维护成本占总测试成本的 40-60%

**第 4 页：LLM 带来的机遇与挑战**
- LLM（GPT-4, DeepSeek, Claude）能理解自然语言，可辅助测试生成
- 但单智能体 LLM 存在明显缺陷：
  - **幻觉问题**：生成 PRD 中没有的功能
  - **缺乏对齐验证**：生成的用例是否覆盖了所有需求？无人检查
  - **一次性生成**：脚本出错后需要人工介入修复

→ **引出问题**：如何让 LLM 生成的测试用例更可靠、更可落地？

### 第 5-7 页 — 核心思路与技术路线（3 页）

**第 5 页：总体方案 — 四层架构**

画一个四层架构图（从上到下）：
```
┌─────────────────────────────────────┐
│  执行自愈层 (Self-Healing)          │  ← 创新点2
│  [运行 → 报错 → 诊断 → 修复]       │
├─────────────────────────────────────┤
│  代码生成层 (POM Code Generation)   │
│  [Page Agent + Test Agent]          │
├─────────────────────────────────────┤
│  多智能体博弈层 (Creator-Auditor)   │  ← 创新点1 ⭐
│  [生成 ⇄ 审计 ⇄ 迭代]              │
├─────────────────────────────────────┤
│  知识检索层 (RAG)                   │
│  [需求文档 → 语义切片 → 向量检索]  │
└─────────────────────────────────────┘
         ↑
     PRD/需求文档（输入）
```

一句话总结：**输入 PRD → RAG 检索需求 → 多智能体博弈生成用例 → 自动生成脚本 → 执行并自愈修复**

**第 6 页：核心创新 1 — Creator-Auditor 博弈**

这是最重要的部分，导师会重点看这里。

- **问题**：单个 LLM 直接生成测试用例，可能编造需求中没有的功能（幻觉）
- **方案**：双 Agent 博弈机制
  1. Case Creator：根据检索到的需求片段，生成测试用例（正/逆向/边界值）
  2. Case Auditor：逐一审计用例，检查是否与需求对齐、有无遗漏场景
  3. 博弈循环：审计不通过 → 退回 Creator 修改 → 直到通过或达到最大迭代次数
- **类比**：就像写论文需要导师审稿，不是写完就完事了

**第 7 页：核心创新 2 — 执行反馈自愈**

- **问题**：生成的测试脚本一跑就报错，每次都要人工修
- **方案**：运行 → 捕获 Traceback + 截图 → 错误分类（定位器失效/超时/断言失败） → Agent 分析根因 → 自动生成修复代码 → 重新运行验证
- **效果**：降低人工介入频率，形成闭环

### 第 11-12 页 — 可行性分析与风险（2 页）

**第 11 页：可行性**
- **技术可行性**：各模块均已跑通核心流程，集成 LLM API 后即可生产真实数据
- **数据可行性**：被测系统 + 需求文档 + 标注用例均为自行构建，可控
- **实验可行性**：评价指标已有定义，消融实验框架已搭建
- **时间可行性**：核心代码已完成，剩余工作为实验调优和论文撰写

**第 12 页：风险与应对**
| 风险 | 概率 | 应对方案 |
|------|------|----------|
| LLM API 费用较高 | 中 | 使用 DeepSeek（更便宜）+ 缓存机制减少调用 |
| 自愈模块定位器修复准确率 | 中 | 论文中如实报告，作为局限性讨论 |
| 导师质疑创新点不够 | 低 | Creator-Auditor 博弈机制是本领域较新思路，有明确学术价值 |
| 实验效果不够"好看" | 中 | 论文重点在于方法设计，而非刷指标；可展示失败的 case 分析 |

### 第 14-15 页 — 请教导师的问题（最重要！）

> 这 2 页是汇报的核心——明确告诉导师你需要他帮你判断什么。

**第 14 页：需要导师指导的问题**

1. **选题可行性**：这个题目（多智能体 + RAG + 测试生成）作为硕士论文，范围和深度是否合适？方向是否明确？

2. **创新点界定**：目前定位的两个创新点——Creator-Auditor 博弈机制 和 执行反馈自愈 —— 学术价值是否足够？是否需要增加或调整？

3. **实验设计**：除了覆盖率、幻觉率、自愈率，还有哪些评价指标能增强论文说服力？是否需要和已有工具（如直接使用 ChatGPT 生成测试）做对比？

4. **案例选择**：使用自建电商平台作为案例是否足够？是否建议找一个开源项目或企业真实系统？

5. **论文侧重点**：目前代码占比 60%（框架实现）+ 40%（实验），导师是否有具体的结构期望？
