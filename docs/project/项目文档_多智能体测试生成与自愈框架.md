## 1. 项目介绍

### 1.1 项目名称

**基于多智能体协同的需求驱动自动化测试生成与自愈框架**。

英文可表述为：

**A Requirement-Driven Automated Test Generation and Self-Healing Framework Based on Multi-Agent Collaboration**。

### 1.2 项目定位

本项目是一套面向软件测试研究与工程验证的智能化测试原型。它以自然语言需求文档为输入，通过需求解析、检索增强生成、多智能体协作、质量审计、自动化代码生成、浏览器执行、故障诊断和测试脚本自愈，形成一条相对完整的自动化测试生产链路。

项目并不是单纯调用大语言模型生成几段测试代码，而是重点解决生成式测试中的四个现实问题：

1. **需求依据不足**：模型生成的测试可能脱离原始需求，产生幻觉或遗漏关键边界场景；
2. **生成结果缺少质量约束**：代码能生成不代表用例正确，更不代表可以直接进入执行环节；
3. **测试脚本容易失效**：页面结构、定位器、等待条件或断言变化会导致自动化脚本频繁失效；
4. **策略成本不可控**：每次都调用大模型进行修改成本较高，固定轮次或固定规则又缺乏场景适应性。

为此，项目引入 Creator–Auditor 多智能体协作、确定性质量闸门、安全门控强化学习、上下文感知自愈策略选择和风险感知测试排序，尝试在测试质量、执行成本和自适应能力之间取得平衡。

### 1.3 项目性质

该项目同时具备三种属性：

| 属性 | 说明 |
|---|---|
| 研究原型 | 用于验证多智能体、强化学习和自愈算法在自动化测试中的可行性 |
| 工程框架 | 已提供命令行入口、模块化代码、测试执行器、结果文件和复现脚本 |
| 论文实验平台 | 支撑硕士论文、开题答辩、算法对比、消融实验和研究汇报 |

### 1.4 当前阶段判断

项目已经完成核心系统骨架和主要算法模块，能够跑通以下链路：

```text
需求文档
  -> 需求解析与语义切片
  -> RAG 检索
  -> Creator 生成测试用例
  -> Auditor 审计与反馈
  -> 质量闸门 / RL-AGS 终止决策
  -> Page Object 与测试脚本生成
  -> Pytest + Playwright 执行
  -> 故障分类
  -> 修复策略选择
  -> 脚本修复与回归复测
```

当前项目的主要任务已经从“搭框架”转向“补证据”：扩大真实故障注入规模、补充真实多轮智能体轨迹、在第二个被测系统上完成同等级复现，并增强统计有效性。

## 2. 项目目标与研究问题

### 2.1 总体目标

构建一套能够从自然语言需求自动生成高质量测试用例和浏览器自动化脚本，并在执行失败后完成诊断、修复和验证的多智能体测试框架。

### 2.2 具体目标

1. 将 Markdown 需求文档转换为可检索的结构化需求知识；
2. 利用 Creator 生成正向、逆向和边界测试用例；
3. 利用 Auditor 检查需求覆盖、逻辑冲突、幻觉和用例完整性；
4. 通过质量闸门阻断未通过审计的测试进入代码生成；
5. 自动生成基于 Page Object Model 的 Playwright 测试代码；
6. 自动执行生成脚本并收集标准输出、错误输出和 Traceback；
7. 对 locator、timeout、assertion、syntax、import 等故障进行分类；
8. 根据上下文选择规则修复、LLM 重写或回退等自愈策略；
9. 在修复后进行回归复测，确认修复是否真正有效；
10. 用强化学习和排序算法降低无效迭代与执行成本。

### 2.3 核心研究问题

| 编号 | 研究问题 | 项目中的对应方案 |
|---|---|---|
| RQ1 | 如何提高需求到测试用例的可追溯性和覆盖完整性？ | 语义切片、RAG、Ground Truth 覆盖评价 |
| RQ2 | 如何降低大模型生成测试中的幻觉和错误接受？ | Creator–Auditor、质量闸门、Safety Gate |
| RQ3 | 如何动态决定继续修改还是接受生成结果？ | RL-AGS、Safe PPO、规则阈值基线 |
| RQ4 | 如何在测试失败后选择高成功率且成本合理的修复策略？ | HSS Bandit、成本敏感 LinUCB |
| RQ5 | 如何优先执行更有价值的测试？ | RCP-TCP 风险与历史信息排序 |
| RQ6 | 框架能否在真实浏览器环境中完成闭环？ | Flask 标靶、Playwright E2E、真实 locator 故障注入 |

## 3. 总体架构

### 3.1 分层架构

项目可以划分为六个层次：

| 层次 | 主要职责 | 核心目录或文件 |
|---|---|---|
| 输入层 | 提供需求文档、Ground Truth 和运行配置 | `experiments/requirements/`、`config.py` |
| 知识层 | 解析需求、语义切片、建立索引和检索 | `framework/rag/` |
| 智能体层 | 生成、审计、反馈和协调多轮协作 | `framework/multi_agent/` |
| 决策优化层 | 终止决策、安全动作投影、自愈策略选择、测试排序 | `framework/rl/` |
| 生成与执行层 | 生成 Page Object 和测试代码，执行测试 | `framework/code_gen/`、`framework/self_healing/executor.py` |
| 评价与实验层 | 计算覆盖、幻觉、自愈成功率并运行对比实验 | `experiments/`、`tests/` |

### 3.2 核心数据流

```text
Markdown 需求
    |
    v
DocumentParser -> SemanticChunker -> Retriever
    |                                  |
    +-------------需求证据-------------+
                                       v
                               CaseCreator（Creator）
                                       |
                                       v
                               CaseAuditor（Auditor）
                                       |
                          审计问题、覆盖估计、幻觉信息
                                       |
                                       v
                     Coordinator + Safety-gated RL-AGS
                         | 接受              | 继续修订
                         v                   +------回到 Creator
                    质量闸门通过
                         |
                         v
               PageAgent + TestAgent
                         |
                         v
              Pytest + Playwright 脚本
                         |
                         v
                  SandboxExecutor
                    |           |
                  成功          失败
                    |           v
                    |    ErrorDiagnoser
                    |           |
                    |    HealingAgent + Bandit
                    |           |
                    +<-----修复后回归复测
```

### 3.3 设计原则

1. **需求证据优先**：测试用例必须能回到需求上下文，而不是让模型自由发挥；
2. **生成与审计分离**：生成者和审计者承担不同职责，避免同一个模型角色自说自话；
3. **确定性规则兜底**：强化学习不能越过安全边界，不安全接受必须被阻断；
4. **失败必须闭环**：修复结果需要复测，不能仅凭代码已修改就宣布成功；
5. **实验结果分级**：真实执行、历史记录和受控模拟分别表述，避免夸大结论；
6. **模块化与可替换**：嵌入后端、LLM 提供商、决策策略和被测系统均保留替换空间。

## 5. 项目内容与核心模块

### 5.1 需求解析模块

核心实现：`framework/rag/document_parser.py`。

该模块负责读取 Markdown 需求文档，将需求中的标题层级、功能描述和正文内容转换为结构化数据。解析结果会附带模块、功能名称、文本内容和来源等元数据，为后续切片和检索提供基础。

主要作用：

- 将非结构化需求转换为机器可处理的数据；
- 保留需求来源，增强测试用例可追溯性；
- 为不同业务模块建立统一输入格式。

### 5.2 语义切片模块

核心实现：`framework/rag/semantic_chunker.py`。

该模块不只按固定字符数粗暴截断，而是优先利用需求结构形成业务语义切片。项目同时保留固定长度切片方法，用于基线实验或降级处理。

现有需求覆盖登录、搜索、购物车和结算四个模块，共形成 80 个需求单元。

### 5.3 检索模块

核心实现：`framework/rag/retriever.py`。

主要能力：

- 构建需求索引；
- 根据自然语言查询返回 Top-K 相关需求；
- 按业务模块过滤需求；
- 支持 Sentence Transformers 语义向量；
- 支持 TF-IDF 确定性降级；
- 在依赖或缓存条件受限时保持基本可复现性。

默认 `RETRIEVAL_TOP_K=3`，默认嵌入后端为 `tfidf`。

### 5.4 Creator 测试用例生成智能体

核心实现：`framework/multi_agent/case_creator.py`。

Creator 根据检索到的需求上下文生成结构化测试用例。用例通常包含：

- 测试编号；
- 所属模块；
- 测试标题；
- 前置条件；
- 操作步骤；
- 预期结果；
- 测试类型；
- 优先级或风险信息。

Creator 重点覆盖正向、逆向和边界场景，并提供 Mock 用例降级能力，使项目在没有真实 LLM 凭据时仍可进行本地流程验证。

### 5.5 Auditor 质量审计智能体

核心实现：`framework/multi_agent/case_auditor.py`。

Auditor 对 Creator 的结果进行独立审查，检查：

- 用例是否有需求依据；
- 是否遗漏关键需求；
- 是否存在幻觉步骤或预期结果；
- 是否存在相互冲突的测试描述；
- 步骤和断言是否完整；
- 是否缺少逆向或边界场景；
- 是否达到进入代码生成阶段的质量要求。

审计结果包括是否通过、问题列表、问题严重程度和总结，可反馈给 Creator 继续修订。

### 5.6 Coordinator 多智能体协调器

核心实现：`framework/multi_agent/coordinator.py`。

Coordinator 是生成阶段的流程控制中心，负责：

1. 启动 Creator 生成初始用例；
2. 调用 Auditor 进行审计；
3. 统计错误、警告、覆盖率和幻觉信息；
4. 根据固定规则或 RL-AGS 决定接受还是继续；
5. 将问题反馈给 Creator；
6. 记录每轮用例、审计结果、决策动作和决策来源；
7. 输出明确的终止状态。

目前定义的关键终止状态包括：

| 状态 | 含义 |
|---|---|
| `accepted_audit` | Auditor 明确通过 |
| `accepted_policy` | 策略判断可以接受，且未触发安全阻断 |
| `failed_max_iterations` | 达到最大轮次仍未通过，流程失败 |

### 5.7 质量闸门

质量闸门是项目从“能生成”迈向“可控制”的关键机制。

只有 `eligible_for_codegen=true` 的用例集才能进入代码生成阶段。达到最大迭代轮次并不等于生成成功；如果仍存在严重问题，Coordinator 会返回 `failed_max_iterations`，Pipeline 将直接隔离这批用例。

这一机制避免了以下错误逻辑：

```text
错误逻辑：已经改了三轮 -> 应该差不多 -> 继续生成代码
正确逻辑：已经改了三轮 -> 仍未通过审计 -> 明确失败并阻断
```

### 5.8 Safety-gated RL-AGS

核心实现：

- `framework/rl/ags_environment.py`；
- `framework/rl/ags_trainer.py`；
- `framework/rl/safe_generation_env.py`。

旧版 RL-AGS 主要学习“接受”或“继续迭代”。新版安全生成环境将动作细分为：

1. 接受结果；
2. 补充覆盖；
3. 修正一致性；
4. 补充边界场景；
5. 刷新需求证据。

安全门控规则用于约束 PPO：当存在 error、幻觉、覆盖不足或证据一致性不足时，系统不允许直接接受，而是将危险动作投影为更合适的修订动作。

这种设计体现了“学习策略负责优化，确定性规则负责守底线”的原则。

### 5.9 Page Object 生成模块

核心实现：`framework/code_gen/page_agent.py`。

PageAgent 从测试用例中识别涉及的页面、输入框、按钮和操作，生成页面对象代码。其价值在于：

- 降低页面定位器与测试业务逻辑的耦合；
- 统一页面操作；
- 页面变化时优先修复 Page Object；
- 使生成测试更接近工程化自动化测试结构。

### 5.10 测试脚本生成模块

核心实现：`framework/code_gen/test_agent.py`。

TestAgent 根据结构化用例和 Page Object 生成 Pytest + Playwright 测试脚本。目前对登录、搜索、购物车和结算模块提供了较完整的专用渲染逻辑，同时保留通用用例渲染能力。

主要生成内容：

- `conftest.py`；
- 页面对象文件；
- 按业务模块拆分的测试文件；
- 页面访问、输入、点击和断言代码；
- 测试数据与环境重置逻辑。

### 5.11 测试执行器

核心实现：`framework/self_healing/executor.py`。

执行器通过独立子进程运行测试，具备：

- 执行普通 Python 脚本或 Pytest 测试；
- 支持 `test_file.py::test_case` node id；
- 捕获 `stdout` 和 `stderr`；
- 设置执行超时；
- 返回退出码、成功状态和耗时；
- 自动补充项目路径到 `PYTHONPATH`；
- 执行 Pylint 静态检查。

需要说明的是，“沙箱”在当前原型中主要指受控子进程和工作目录隔离，并不等同于容器级或操作系统级安全沙箱。

### 5.12 错误诊断模块

核心实现：`framework/self_healing/error_diagnoser.py`。

诊断器从测试执行日志和 Traceback 中识别故障模式，支持的主要类别包括：

- locator；
- timeout；
- assertion；
- syntax；
- attribute；
- import；
- unknown。

诊断结果会提供错误类别、命中证据、Traceback 摘要和修复建议，供 HealingAgent 使用。

### 5.13 HealingAgent 自愈模块

核心实现：`framework/self_healing/healing_agent.py`。

HealingAgent 负责：

1. 根据故障类别和上下文选择修复策略；
2. 执行规则修复、LLM 重写、超时调整或回退；
3. 生成修复后的脚本；
4. 保存修复版本；
5. 调用执行器进行回归复测；
6. 将成功或失败结果反馈给策略选择器。

当前策略包括：

| 策略 | 说明 |
|---|---|
| `rule_locator` | 根据常见 Playwright 定位器问题进行规则修复 |
| `rule_timeout` | 调整等待和超时逻辑 |
| `llm_rewrite` | 利用 LLM 根据错误上下文重写代码 |
| `fallback` | 使用保守回退方案 |

### 5.14 上下文感知自愈 Bandit

核心实现：`framework/rl/contextual_healing_bandit.py`。

该模块采用 LinUCB 对自愈策略进行在线选择。上下文特征包括：

- 错误类别；
- 定位器类型；
- DOM 变化程度；
- 当前重试次数；
- 脚本复杂度；
- 历史修复成功率；
- 估算调用成本。

奖励函数同时考虑：

- 是否修复成功；
- 回归测试是否通过；
- 策略调用成本；
- 多次重试成本。

因此，该模块追求的不是单纯最大化修复率，而是最大化质量与成本共同约束下的综合收益。

### 5.15 RCP-TCP 测试优先级排序

核心实现：`framework/rl/test_prioritizer.py`。

排序因素包括：

- 需求覆盖贡献；
- 功能风险等级；
- 历史失败信息；
- 边界场景属性；
- 预计执行成本。

该模块适用于测试时间受限场景，目标是在有限执行窗口中优先运行更可能暴露问题或更具业务价值的用例。

### 5.16 评价模块

核心实现：`experiments/evaluation.py`。

主要指标包括：

- 需求覆盖率；
- 幻觉率；
- 自愈成功率；
- RL 收敛情况；
- 固定策略与学习策略对比；
- 带 Auditor 与不带 Auditor 的消融对比。

### 5.17 端到端 Pipeline

核心实现：`framework/multi_agent/pipeline.py`。

Pipeline 将所有模块串联为可复现流程：

```text
构建 RAG
  -> 分模块运行 Creator–Auditor
  -> 筛选通过质量闸门的用例
  -> 生成 Page Object 和测试代码
  -> 可选执行测试
  -> 可选自愈失败脚本
  -> 计算指标
  -> 保存 JSON 实验报告
```

## 6. 完整业务流程

### 6.1 输入准备

需求文档位于：

- `experiments/requirements/login_requirements.md`；
- `experiments/requirements/search_requirements.md`；
- `experiments/requirements/cart_requirements.md`；
- `experiments/requirements/checkout_requirements.md`。

对应 Ground Truth 位于 `experiments/ground_truth.json`。

### 6.2 RAG 建库

系统解析需求并形成语义切片，然后使用 TF-IDF 或 Sentence Transformers 构建索引。生成某个业务模块的测试前，Retriever 会筛选该模块的需求证据。

### 6.3 测试用例生成与审计

Creator 生成结构化测试用例；Auditor 对用例进行审计。若不通过，Coordinator 将问题反馈给 Creator 并进入下一轮。

### 6.4 终止决策与质量准入

系统可以使用固定迭代策略、规则阈值或 RL-AGS 决策。无论使用哪种策略，Safety Gate 都会阻止明显不安全的接受动作。最终只有审计通过或合法策略接受的结果能进入代码生成。

### 6.5 自动化代码生成

PageAgent 生成页面对象，TestAgent 生成按模块拆分的 Pytest + Playwright 测试文件。

### 6.6 执行与结果采集

执行器启动测试进程，收集执行结果。目标系统可以由 `target_app/` 本地启动，健康检查地址为 `http://localhost:5000/health`。

### 6.7 故障诊断与自愈

若测试失败，诊断器提取错误类别和证据；HealingAgent 选择修复策略，生成修复脚本并再次执行。只有回归复测通过，修复才被记录为成功。

### 6.8 评价与持久化

最终结果以 JSON 保存到 `experiments/results/`，内容可包括：

- 运行编号；
- 模块列表；
- 生成用例数；
- 每轮生成与审计历史；
- 生成文件列表；
- 执行与自愈结果；
- 覆盖率、幻觉率和自愈成功率。

### 9.5 生成策略基准

实验设置：3 个训练种子，每个种子训练 50,000 步，在共享的 500 个场景上评价。

| 策略 | 接受率 | 不安全接受率 | 平均迭代 | 平均成本 | 平均奖励 |
|---|---:|---:|---:|---:|---:|
| 固定 1 轮 | 13.00% | 87.00% | 1.000 | 0.000 | -26.308 |
| 固定 3 轮 | 49.40% | 50.60% | 3.000 | 1.519 | 2.746 |
| 固定 5 轮 | 83.40% | 16.60% | 5.000 | 2.761 | 22.215 |
| 审计阈值规则 | 89.60% | 0.00% | 3.566 | 2.014 | 28.244 |
| 原始 PPO | 87.67% | 2.47% | 3.984 | 2.302 | 26.815 |
| Safe PPO | **90.13%** | **0.00%** | 3.907 | 2.180 | **28.766** |

实验说明 Safe PPO 在受控环境中消除了不安全接受，并取得较高综合奖励。但该实验使用受控状态转移，不等同于真实 Creator–Auditor 在线交互。

### 9.6 自愈策略基准

实验设置：6 类故障、6 类策略、10 个随机种子、每个种子 5,000 次在线决策。

| 策略 | 修复成功率 | LLM 调用率 | 平均成本 | 平均奖励 |
|---|---:|---:|---:|---:|
| 固定规则 | 70.94% | 33.25% | 0.373 | 0.341 |
| ε-greedy | 68.12% | 54.19% | 0.533 | 0.217 |
| UCB1 | 71.83% | 49.97% | 0.505 | 0.311 |
| 始终调用 LLM | 70.90% | 100.00% | 0.900 | 0.142 |
| 成本敏感 LinUCB | **76.23%** | 62.84% | 0.606 | **0.367** |
| Oracle 上界 | 79.57% | 56.28% | 0.555 | 0.458 |

LinUCB 相比固定规则的平均奖励提高 0.026，近似 95% 置信区间为 `[0.002, 0.050]`。相比始终调用 LLM，成功率提高 5.332 个百分点，LLM 调用率降低 37.16 个百分点。

该实验是配对潜在结果模拟，不是 50,000 次真实浏览器故障。它支持算法可行性，但还不能替代大规模真实注入实验。

## 13. 当前优势、局限与风险

### 13.1 项目优势

1. **链路完整**：不是单点 Demo，覆盖需求、生成、审计、执行和修复；
2. **质量意识较强**：明确区分“轮次结束”和“质量通过”；
3. **研究与工程结合**：既有算法基准，也有真实 Playwright 闭环；
4. **支持无 LLM 降级**：TF-IDF 和 Mock 使基础流程可重复运行；
5. **证据产物较全**：JSON、图表、轨迹、生成脚本和论文材料均有保留；
6. **安全设计合理**：学习策略之外有确定性质量底线；
7. **具备扩展基础**：已准备 Spree 作为第二被测系统。

### 13.2 当前局限

1. 主要真实 E2E 证据集中在单一 Flask 标靶；
2. 真实 Creator–Auditor 多轮轨迹不足，Safe PPO 主要在受控环境评价；
3. LinUCB 的大规模结果来自模拟故障响应，不是真实浏览器执行；
4. 真实自愈闭环目前主要证明 locator 故障；
5. Ground Truth 由项目内部构建，可能存在标注偏差；
6. RCP-TCP 的历史失败样本过少，尚不足以支持强泛化结论；
7. “沙箱执行”不是强安全隔离，执行不可信生成代码仍有风险；
8. 当前工作区存在未提交修改和大量未跟踪产物，可复现版本基线不够干净；
9. README 的 26 条快速验证与报告中的 80 条历史套件口径不同，需要继续统一说明；
10. 项目依赖较多，`requirements.txt` 未锁定精确版本，长期复现可能出现漂移。

### 13.3 主要工程风险

| 风险 | 影响 | 建议 |
|---|---|---|
| 直接执行模型生成代码 | 可能访问文件、网络或系统资源 | 使用容器、低权限账户和资源限制 |
| 测试环境状态污染 | 导致结果不稳定 | 强制 reset、独立数据、幂等清理 |
| LLM 输出格式漂移 | JSON 解析失败或字段缺失 | Schema 校验、重试和严格解析 |
| 需求与 Ground Truth 同源偏差 | 指标过于乐观 | 引入双人标注、独立评审和一致性统计 |
| 依赖与浏览器版本漂移 | E2E 复现失败 | 锁版本、容器化、记录浏览器版本 |
| 受控模拟过多 | 论文结论外部有效性不足 | 增加真实故障注入和跨系统实验 |

## 14. 后续工作建议

### 14.1 第一优先级：固化可复现基线

1. 整理 `.gitignore`，排除缓存、临时图表和中间产物；
2. 提交当前核心代码、测试和关键实验结果；
3. 创建可复现版本标签；
4. 增加锁定依赖文件；
5. 在实验 JSON 中写入 Git commit、Python 版本、浏览器版本和配置摘要。

### 14.2 第二优先级：重跑真实 E2E

1. 在干净环境重新执行 26 条快速验证；
2. 重新执行 80 条完整 E2E；
3. 输出 JUnit XML、执行时间和失败截图；
4. 将执行结果与生成报告绑定，避免“生成报告”和“执行报告”分离。

### 14.3 第三优先级：扩大真实故障注入

对以下故障分别构造真实 Playwright 实例：

- locator；
- timeout；
- assertion；
- test data；
- syntax；
- import。

每类应进行多次重复、记录修复尝试数、成功率、耗时、LLM Token 和回归结果，并与固定规则、总是调用 LLM、UCB1、LinUCB 进行真实对比。

### 14.4 第四优先级：补充真实多智能体轨迹

1. 采集真实 Creator–Auditor 多轮交互；
2. 标注每轮覆盖、幻觉、冲突和安全状态；
3. 用真实轨迹训练和评估 PPO；
4. 与规则阈值、固定轮次进行成对比较；
5. 报告置信区间和失败案例，而不是只报平均值。

### 14.5 第五优先级：完成 Spree 跨系统验证

1. 确定 Spree 的稳定本地版本和种子数据；
2. 对登录、搜索、购物车和结算建立独立 Ground Truth；
3. 运行同一生成 Pipeline；
4. 对比 Flask 与 Spree 的覆盖、幻觉、生成成功率和自愈成功率；
5. 明确哪些规则可以迁移，哪些依赖具体页面实现。

### 14.6 第六优先级：增强缺陷发现证据

仅证明生成测试“都能通过”还不够，因为一套永远通过的测试可能啥 Bug 也抓不着。建议增加：

- 变异测试；
- 人工注入业务缺陷；
- 真实历史 Bug；
- 缺陷检出率；
- Mutation Score；
- APFD / APFDc；
- 与人工测试或传统自动化脚本的对比。

这一步对论文含金量提升最大，因为它回答了真正关键的问题：生成出来的测试到底有没有发现缺陷的能力。

## 15. 项目总结

本项目已经完成一套较完整的需求驱动智能测试研究原型。系统以自然语言需求为起点，通过 RAG 建立需求证据，利用 Creator–Auditor 多智能体协作生成和审计测试用例，再由质量闸门和 Safety-gated RL-AGS 控制生成准入，最后自动生成并执行 Pytest + Playwright 脚本。测试失败后，系统可以完成错误分类、修复策略选择、代码修改和回归验证。

从工程成果看，项目已经具备明确的模块边界、统一命令入口、自动化验证脚本、真实浏览器标靶、专项单元测试和机器可读实验产物。从算法成果看，项目已经实现安全门控生成决策、成本敏感上下文自愈 Bandit 和风险感知测试排序，并完成了相应受控基准、消融实验和真实 locator 自愈案例。

项目当前最需要补强的不是继续堆叠新算法，而是提高证据强度：重跑并固化完整 E2E，扩大真实故障注入，采集真实多智能体轨迹，在 Spree 上完成跨系统验证，并用变异测试或真实缺陷证明测试的缺陷发现能力。只有把这些环节补齐，项目才能从“功能完整、实验好看”的研究原型，进一步升级为“结论可信、可复现、具备外部有效性”的高质量研究成果。
