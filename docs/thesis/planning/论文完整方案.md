## 二、三个创新点（开题核心）

### 创新点 1：Creator-Auditor 对抗博弈机制

| 项目 | 内容 |
|------|------|
| **定位** | 基础框架，论文的第 3 章主体 |
| **解决什么问题** | LLM 生成测试用例时的"幻觉"问题——生成需求中不存在的功能 |
| **方法** | Creator 负责生成覆盖正向/逆向/边界值的用例，Auditor 从一致性和完备性两个维度审计，不通过则迭代重写 |
| **现有代码** | ✅ 已完成（`case_creator.py` / `case_auditor.py` / `coordinator.py`） |
| **需要改什么** | 用 AutoGen 的 `AssistantAgent` + `GroupChat` 重写通信层 |

### 创新点 2：基于执行反馈的自动化脚本自愈机制

| 项目 | 内容 |
|------|------|
| **定位** | 闭环反馈，论文的第 3 章后半部分 |
| **解决什么问题** | 生成脚本因元素定位器变更、超时等环境变化导致执行失败，人工修复成本高 |
| **方法** | 沙箱执行 → 错误捕获分类 → Agent 分析修复 → 重执行验证 |
| **现有代码** | ✅ 已完成（`executor.py` / `error_diagnoser.py` / `healing_agent.py`） |
| **需要改什么** | 用 AutoGen 重写 HealingAgent，增加基于规则和基于 LLM 的混合修复策略 |

### 创新点 3：基于强化学习的智能体协作优化 ← 新增核心算法贡献

| 项目 | 内容 |
|------|------|
| **定位** | **论文的核心算法创新**，贯穿博弈和自愈两个阶段 |
| **解决什么问题** | Creator-Auditor 固定轮次效率低、Healing 策略单一无学习能力 |
| **子模块 A** | **RL-AGS（RL-based Adaptive Game Stopping）**：用 PPO 动态决定博弈何时终止 |
| **子模块 B** | **RL-HSS（RL-based Healing Strategy Selection）**：用 Multi-Armed Bandit 选择最佳修复策略 |
| **工具** | `stable-baselines3`（PPO）+ `gymnasium`（环境定义） |
| **预期成果** | 收敛曲线图、奖励曲线图、与固定策略的对比实验 |

### 关键数据流

```
① 需求文档 → RAG 解析 → 语义切片 → 向量检索
② 需求片段 → Creator 生成用例 → Auditor 审计
                ↑                      │
                └── RL-AGS 判断是否重来 ──┤
                                         ▼
③ 通过用例 → PageAgent 生成 POM → TestAgent 生成 Pytest
④ 执行脚本 → 错误诊断 → RL-HSS 选择策略 → 修复 → 重执行
⑤ 修复成功/失败 → 更新 RL-HSS 模型 → 继续学习
```

## 七、开题答辩常见问题准备

| 可能被问的问题 | 怎么回答 |
|--------------|---------|
| **"你的方法比 MetaGPT 好在哪？"** | MetaGPT 是通用软件开发框架，测试只是其 QAEngineer 一个角色；本文专注测试领域，且引入 RL 优化博弈和自愈，在测试场景上更深入 |
| **"RL 在这为什么是必要的？"** | 固定轮次要么浪费（质量够了还在跑）要么不足（没跑够就停了）。RL 能根据当前状态动态决策，平衡质量和成本。实验数据会证明 RL 比任何固定轮次都好 |
| **"自愈的创新在哪？"** | 传统自愈是规则驱动（固定匹配替换），本文引入了 RL 选择不同修复策略，系统能根据历史修复效果持续优化选择 |
| **"你自己实现的还是用了开源？"** | 多智能体通信基于微软 AutoGen，RL 算法基于 Stable-Baselines3，在它们之上构建测试专用的环境、奖励函数和策略 |
| **"工作量够吗？"** | 3 个创新点 + 6 组消融实验 + 两个开源框架集成 + 完整电商系统案例，工作量是充分的 |
