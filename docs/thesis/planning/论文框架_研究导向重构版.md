# 硕士论文研究导向大纲（重构版）

## 一、论文定位

### 建议题目

**面向需求驱动 Web 自动化测试的多智能体安全生成与自适应修复方法研究**

备选题目：

1. 面向自动化测试的多智能体用例生成控制与自适应修复方法研究
2. 基于安全强化学习与上下文多臂老虎机的自动化测试生成与修复方法研究

### 核心定位

论文不再以“搭建完整测试智能体平台”为核心贡献，而是研究自动化测试闭环中的两个决策问题：

1. 测试用例经过多轮生成和审计后，系统如何在质量与成本之间安全地决定下一步动作。
2. 自动化脚本执行失败后，系统如何根据故障上下文选择成功率高、成本低的修复策略。

现有工程系统承担算法实现、数据采集和实验验证功能，不再作为论文的主要创新点。

## 二、研究痛点与研究问题

### 痛点一：生成结果缺少可计算的质量状态

大语言模型生成的测试用例可能存在需求无依据、场景遗漏、边界条件不明确等问题。仅依靠自然语言评价，难以为后续决策算法提供稳定状态。

解决思路：将需求覆盖、证据一致性、错误类型和问题严重程度转化为结构化质量状态，为算法一提供输入。

### 痛点二：固定轮次与无约束策略无法兼顾质量和成本

固定迭代轮次无法适应不同难度的需求。简单需求可能浪费调用成本，复杂需求可能在质量不足时结束。原始 PPO 还可能在存在严重错误时错误接受结果。

研究问题 RQ1：在多智能体测试生成过程中，如何利用审计反馈动态选择接受、继续修订或切换修订策略？

研究问题 RQ2：如何保证学习型策略不会接受包含严重错误的测试用例，同时减少无效迭代和模型调用？

### 痛点三：固定自愈策略无法适应不同故障上下文

定位器冲突、等待超时、断言变化和测试数据污染所需的修复方式不同。固定规则覆盖范围有限，而所有故障都调用大模型会增加成本并引入新的代码风险。

研究问题 RQ3：如何根据错误类型、脚本特征和历史修复反馈，在线选择成功率高且成本可控的修复策略？

## 三、两项核心算法

## 算法一：证据约束的安全自适应生成控制算法

### 1. 算法目标

该算法控制 Creator-Auditor 的多轮协作过程。它不负责直接生成文本，而是根据每轮审计结果决定：

- 接受当前测试用例集；
- 针对需求遗漏重新生成；
- 针对幻觉或不一致问题重新生成；
- 补充边界场景；
- 刷新需求证据后重新生成；
- 达到最大轮次后异常结束并转人工处理。

### 2. 质量状态构建

每轮状态至少包括：

| 状态特征 | 含义 |
|---|---|
| 当前轮次 | 已执行的生成审计轮次 |
| ERROR 数量 | 可能影响正确性的严重问题数 |
| WARNING 数量 | 描述不清或边界不明确的问题数 |
| 幻觉问题数 | 无法追溯到需求证据的用例数 |
| 需求覆盖率 | 已覆盖需求点占全部需求点的比例 |
| 覆盖率增量 | 当前轮相对上一轮的覆盖提升 |
| 证据一致性 | 用例与需求证据的匹配程度 |
| 重复用例率 | 当前用例集中重复或高度相似用例的比例 |
| 累计调用成本 | Token、时间或模型调用次数 |

当前代码只有轮次、问题数、粗略覆盖率和幻觉标记，后续必须补充错误分型、覆盖变化和真实调用成本，否则 PPO 看到的状态过于粗糙。

### 3. 动作空间

不再只设置“继续”和“接受”两个动作，建议扩展为：

| 动作 | 作用 |
|---|---|
| ACCEPT | 接受当前结果并进入代码生成 |
| REVISE_COVERAGE | 根据遗漏需求补充用例 |
| REVISE_CONSISTENCY | 删除或修正无需求依据的用例 |
| REVISE_BOUNDARY | 补充或明确边界场景 |
| REFRESH_EVIDENCE | 扩大或调整需求检索范围后重新生成 |

细分修订动作可以验证策略是否真正学会“根据问题选择修订方式”，研究价值高于单纯判断继续还是停止。

### 4. 安全约束

学习策略不能直接控制最终放行，必须先计算安全动作集合：

1. 存在 ERROR 时，禁止选择 ACCEPT。
2. 需求证据为空或证据一致性低于阈值时，禁止选择 ACCEPT。
3. 达到最大轮次但审计未通过时，状态记为 `FAILED_REVIEW`，禁止进入代码生成。
4. Auditor 通过后才允许正常进入代码生成。

当前代码只实现了第一条的部分逻辑，第三条最终质量闸门尚未实现。

### 5. 奖励设计

奖励函数不需要堆很多花哨符号，围绕三类因素即可：

- 质量收益：覆盖率提高、一致性提高、审计通过时给予正奖励。
- 风险惩罚：严重错误、幻觉和不安全接受给予较大负奖励。
- 成本惩罚：每增加一轮、一次模型调用或一段 Token 消耗给予小额负奖励。

奖励的核心目标是：在满足质量约束的前提下，用尽可能少的迭代获得可接受结果。

### 6. 策略学习

基础策略采用 PPO。PPO 是已有算法，论文创新不能写成“提出 PPO”，而应写成：

- 面向测试审计反馈设计状态空间；
- 设计问题类型驱动的细粒度修订动作；
- 设计质量与成本联合奖励；
- 设计不可接受状态的安全动作约束；
- 将真实生成审计轨迹用于训练和评价。

策略执行顺序如下：

```text
Creator 生成测试用例
        ↓
Auditor 输出结构化问题与需求证据
        ↓
构建当前质量状态
        ↓
根据安全规则计算允许动作
        ↓
PPO 在允许动作中选择下一步策略
        ↓
接受 / 定向修订 / 刷新检索 / 异常结束
```

### 7. 训练数据

不能继续只用几个静态状态训练或评价。需要采集真实多轮轨迹：

1. 从原始需求构造完整、缺失、冲突、模糊和噪声版本。
2. 使用多个 Prompt 模板和随机种子生成不同质量的测试用例。
3. 每轮记录需求证据、生成用例、审计问题、动作、质量变化、Token 和耗时。
4. 按业务模块或被测系统划分训练集和测试集，避免同一需求同时出现在训练和测试中。

### 8. 对比方法

- 固定 1 轮、3 轮和 5 轮；
- 审计通过即停止的规则策略；
- 无安全约束的原始 PPO；
- 只有继续和接受两个动作的 PPO；
- 本文提出的证据约束安全策略。

### 9. 评价指标

- 最终审计通过率；
- 不安全接受率；
- 需求覆盖率和幻觉率；
- 平均迭代轮次；
- 平均模型调用次数、Token 和耗时；
- 达到相同质量时的成本；
- 不同随机种子下的均值和方差。

### 10. 消融实验

- 去掉安全约束；
- 去掉覆盖率增量；
- 去掉调用成本惩罚；
- 将细粒度动作退化为继续或接受；
- 去掉需求证据一致性特征。

## 算法二：成本敏感的上下文多臂老虎机自愈策略选择算法

### 1. 算法目标

自动化脚本执行失败后，根据当前故障上下文选择修复策略，使修复成功率提高，同时减少不必要的大模型调用和重复尝试。

### 2. 为什么不能继续使用当前 ε-greedy

当前 RL-HSS 主要按照错误类别保存每种策略的 Q 值，无法区分同一错误类别中的不同上下文。例如，同为 locator 错误，元素重命名、元素重复和页面尚未加载需要的修复方法并不相同。

建议升级为 **LinUCB 上下文多臂老虎机**。LinUCB 是成熟算法，样本效率较高、实现复杂度可控，并能解释哪些上下文特征影响了策略选择。

### 3. 上下文特征

| 特征 | 示例 |
|---|---|
| 错误类别 | locator、timeout、assertion、data、syntax |
| 错误关键词 | strict mode、not found、timeout 等 |
| 定位器类型 | CSS、文本、role、XPath |
| 页面变化程度 | DOM 节点变化比例或候选元素数量 |
| 已失败次数 | 当前脚本已尝试修复的次数 |
| 脚本复杂度 | 代码长度、页面跳转数、断言数量 |
| 历史策略效果 | 相似故障下各策略成功率和耗时 |
| 资源成本 | 预计 LLM Token、执行时间和重试次数 |

### 4. 策略臂

- 规则化定位器修复；
- 等待条件或超时策略调整；
- 断言修复；
- 测试数据或状态重置；
- 大模型局部重写；
- 回退或转人工处理。

策略池必须与实际可执行的修复器一一对应，不能只在配置文件里写名字。

### 5. 成本敏感奖励

奖励由修复效果和成本共同决定：

- 修复后原失败用例通过，给予主要正奖励；
- 修复后回归用例仍通过，再给予额外奖励；
- 修复失败、引入新失败或超过最大尝试次数，给予负奖励；
- LLM 调用、执行耗时和重复尝试产生成本惩罚。

这样可以避免算法为了成功率无脑选择成本最高的大模型重写。

### 6. LinUCB 决策过程

对每个修复策略维护一套参数。每次故障发生时：

1. 将诊断结果转换为上下文向量。
2. 计算每种可用修复策略的预期收益及探索加成。
3. 选择得分最高的策略。
4. 在隔离环境中执行修复并运行目标用例和小规模回归集。
5. 根据成功、耗时和成本计算奖励。
6. 在线更新被选择策略的参数。

### 7. 安全约束

- 修复代码必须先通过语法和静态检查；
- 修改业务断言时必须能够追溯到需求证据；
- 修复后必须执行目标用例和相关回归用例；
- 连续失败达到阈值后停止自动修改并回退；
- 保存补丁和运行记录，保证修改可恢复。

### 8. 故障注入数据集

至少构造以下故障类型，每种类型包含多个实例：

- 元素 ID、文本或 role 变化；
- 多元素匹配导致 strict mode 冲突；
- 页面异步加载和等待不足；
- 断言文本或业务结果变化；
- 测试数据失效、库存污染或登录状态失效；
- Python 语法、导入或属性调用错误。

每个故障实例记录真实可用修复策略，用于评价成功率和策略后悔值。

### 9. 对比方法

- 固定规则优先级；
- 随机选择；
- 当前 ε-greedy；
- UCB1；
- 所有故障均调用 LLM；
- 本文提出的成本敏感 LinUCB；
- 已知最优策略，作为实验上界而非实际算法。

### 10. 评价指标

- 修复成功率；
- 首次修复成功率；
- 平均修复尝试次数；
- 平均修复时间；
- 平均 LLM 调用次数和 Token 成本；
- 修复后回归通过率；
- 累积奖励和累积后悔值；
- 不同故障类型下的策略选择分布。

### 11. 消融实验

- 去掉错误上下文，只按总体成功率选择；
- 去掉成本惩罚；
- 去掉历史反馈；
- 去掉回归验证奖励；
- 将 LinUCB 退化为当前 ε-greedy。

## 第6章 实验设计与结果分析

### 6.1 研究问题与实验假设

- H1：安全自适应控制能够降低不安全接受率。
- H2：在相近生成质量下，该方法能够减少平均迭代轮次和调用成本。
- H3：上下文 LinUCB 在多类故障下能够提高修复收益并减少 LLM 调用。

### 6.2 实验对象与数据集

- 当前 Flask 电商系统可以保留，但不能作为唯一实验对象；
- 增加至少两个规模和业务结构不同的被测系统；
- 构建需求扰动集、真实生成轨迹集和多类型故障注入集；
- 对关键质量标签进行人工复核，报告标注规则和一致性。

### 6.3 算法一对比实验

- 固定轮次、规则停止、原始 PPO和本文算法对比；
- 报告质量、风险、轮次、时间和 Token 成本；
- 至少使用多个随机种子并报告均值、标准差或置信区间。

### 6.4 算法一消融与参数敏感性实验

- 安全约束、状态特征、动作空间和成本惩罚消融；
- 最大轮次、奖励权重和检索范围敏感性分析。

### 6.5 算法二对比实验

- 固定规则、随机、ε-greedy、UCB1、总是 LLM 和 LinUCB 对比；
- 按故障类型分别报告成功率、时间、调用次数和回归结果。

### 6.6 算法二消融与在线学习分析

- 上下文特征、成本项和历史反馈消融；
- 绘制累计奖励、后悔值和策略选择比例随轮次的变化。

### 6.7 端到端系统验证

只用于说明前两项算法能在完整流水线中运行，不把“80 passed”当作算法优越性的核心证据。

### 6.8 威胁与局限性

- 被测系统代表性；
